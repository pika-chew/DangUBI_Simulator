# 시뮬레이터 사용 안내

전체 조건 또는 수동 OBD 입력 → 일정/데이터 생성 → 송신 없는 확인 또는 TLS MQTT 전송을 지원합니다. 새 전체 조건 일정은 운행 1회당 최소·최대 시간을 지정하며 하루 목표 시간은 사용하지 않습니다.

## 컨테이너 실행과 ECR 이미지 관리

화면·FastAPI 제어기·Go 생성/송신 Worker를 Linux 이미지 하나에 포함합니다. 제어기는 한 프로세스로 실행하며 여러 컨테이너로 같은 실행을 자동 분산하지 않습니다. 최신 전체 조건 배정의 기본값은 Microtrip 2초·1회 운행 3~120분·일별 미운행 확률20%입니다. 명시적으로 저장한 기존 운행 범위는 유지합니다.

Docker의 Linux 실행 엔진이 준비된 환경에서 저장소 루트에서 실행합니다.

```powershell
python scripts/container.py build --image dangubi-simulator:local-check
python scripts/smoke_container.py --image dangubi-simulator:local-check
docker run --detach --name dangubi --publish 127.0.0.1:8080:8080 --mount type=volume,source=dangubi-data,target=/data --stop-timeout 30 dangubi-simulator:local-check
```

`smoke_container.py`는 외부 네트워크를 차단한 별도 컨테이너와 임시 볼륨을 만들어 화면·OBD 생성·실행 중 정상 종료·컨테이너 교체 후 기록/조회 캐시 보존을 검사하고 자신이 만든 자원만 정리합니다. 실제 MQTT 접속은 하지 않습니다. Docker context를 지정하려면 빌드 명령은 `python scripts/container.py --context 이름 build ...`, 검사 명령은 `python scripts/smoke_container.py --context 이름 --image ...`로 실행합니다. 기본 context 설정은 변경하지 않습니다.

화면은 http://127.0.0.1:8080 입니다. 종료는 `docker stop --time 30 dangubi`입니다. `/data`의 볼륨을 유지하고 컨테이너를 교체하면 실행 기록과 조회 캐시를 다시 사용할 수 있습니다. 볼륨 삭제는 기록 삭제이므로 주의하세요. 실행 도중 교체하지 말고 정상 종료 후 교체합니다. 강제 종료 시 이전 실행은 중단 상태로 표시하며 자동으로 이어 보내지 않습니다. 기본 이미지에는 인증·HTTPS 계층이 없으므로 AWS에서는 사설 접근 또는 별도 인증된 접근 경로를 구성해야 합니다.

| 환경변수 | 역할 | 컨테이너 기본값 |
|---|---|---|
| DANGUBI_DATA_DIR | 실행 기록·조회 캐시 기본 디렉터리 | /data |
| DANGUBI_DB | 실행 기록 DB 개별 경로 | /data/runs.sqlite3 |
| DANGUBI_CHECKPOINT_DB | 조회용 상태 캐시 개별 경로 | /data/obd-state.sqlite3 |
| DANGUBI_WORKER | Go 실행 파일 경로 | /opt/dangubi/bin/worker |
| DANGUBI_MQTT_PROFILE | MQTT 서버 프로필 경로 | /run/secrets/mqtt.json |

로컬 실행에서 환경변수를 생략하면 기존 `.local` 경로를 사용합니다. 상대 경로는 프로젝트 루트 기준입니다. 데이터 디렉터리보다 개별 DB 경로 설정이 우선합니다. UID/GID10001의 일반 사용자로 실행하므로 호스트 폴더를 연결할 때는 해당 사용자의 쓰기 권한을 준비해야 합니다. 동일 데이터 볼륨을 여러 제어기에 동시에 연결하지 않습니다.

MQTT를 사용할 때 프로필과 인증서를 이미지에 복사하지 않고 읽기 전용으로 연결합니다.

```powershell
docker run --detach --name dangubi --publish 127.0.0.1:8080:8080 --mount type=volume,source=dangubi-data,target=/data --mount type=bind,source=C:/absolute/private/dangubi,target=/run/secrets,readonly --stop-timeout 30 dangubi-simulator:local-check
```

호스트 경로는 실제 준비한 디렉터리로 바꾸고, `mqtt.json`의 인증서/키 경로는 컨테이너 안의 `/run/secrets/...`로 지정합니다. Linux 호스트의 소유권/파일 권한도 확인합니다. `enabled`·`contract_reviewed`·서버 상한 및 화면 송신 확인은 기존대로 적용합니다.

검증한 이미지는 준비된 ECR private 저장소로 업로드합니다. AWS CLI와 대상 저장소 접근 권한이 필요합니다. 아래 계정·리전·저장소·태그는 실제 대상으로 바꿉니다.

```powershell
python scripts/container.py push --image dangubi-simulator:local-check --account 123456789012 --region ap-northeast-2 --repository dangubi-simulator --tag git-COMMIT_ID
```

업로드 명령은 기존 저장소를 확인하고 로컬 이미지 ID를 태그해 전송합니다. 리소스 생성·배포는 수행하지 않습니다. AWS CLI 프로필은 `--profile 이름`으로 선택하며 비밀 값을 인수로 받지 않습니다. ECR 인증 토큰은 Docker의 표준 입력으로 전달하고 Docker의 자격증명 보관 설정을 사용합니다. 출력되는 `digest_reference`를 배포 버전 식별에 사용하세요. `latest`는 업로드 태그로 허용하지 않습니다. ECR에서도 버전 태그 변경을 막는 정책을 권장합니다. 기본 이미지는 Linux/amd64이며 ARM은 `build --platform linux/arm64`로 별도 빌드·실행 검증합니다. 기반 이미지 버전은 Dockerfile의 ARG에서 지정하며 정식 배포 시 digest 고정도 검토합니다.

`.dockerignore`는 제품 빌드에 필요한 경로만 허용합니다. 로컬 실행 데이터·인증서·개인 키·대화/검토 문서·보조 계산기는 빌드 입력에서 제외합니다. 기본 동작은 송신 없음입니다.

### 운영 목표와 현재 실행 한도

운영 지원 목표는 차량25,000대·실행30일, 연결 풀 기본/차량별 연결 병행, 접속 상한 전체1,000회/초·풀500개를 기준으로 준비합니다. 생성 조건·연결 수·배정은 실행 전 설정하고 실행 중 고정합니다. 발행 지연의 초기 검증 목표는 정상 구간 p95 1초/p99 2초이며 실제 보장 수치가 아닙니다.

일정 실행은 아래 소량 시험/운영 프로필에 따라 범위가 다릅니다. 컨테이너 패키징이나 운영 입력 범위가 실제25,000대 처리량·30일 안정성을 보장하는 것은 아닙니다. 풀500개의 최대 부하 수용 여부도 PUBACK·발행 지연·배정 부하를 측정해 판단합니다.

### 소량 시험과 운영 실행

전체 조건의 `실행 프로필`에서 선택합니다. 소량 시험은 기존100대·실행1시간·10,000메시지 제한을 유지합니다. 운영은 전체 조건으로 만든 차량 일정에 최대25,000대·30일을 지정하고 순차 생성 경로로 실행합니다. 개별 수동 일정 편집은 기존 소량 범위입니다.

| 항목 | 운영 경로 |
|---|---|
| 생성 조건 | 기본2초·1회 운행3~120분·일별 미운행 확률20%, 실행 전 변경 가능 |
| 연결 배정 | 기본 연결 풀, Client 수 미지정 시 min(500,차량 수), 차량별 연결도 선택 가능 |
| 생성 처리 | 차량 배정은 실행 시작 시 한 번 계산하고 현재 운행·마지막 상태를 차량별로 유지 |
| 버퍼 | 기본 생성2,000건/8MiB, 운영 송신은 Client 수에 따른100~4,096명령/8MiB |
| 표시 범위 | 차량 목록·배정표는 처음100대, 전체 차량은 실제 실행 대상 |
| 다른 차량 조회 | 차량 번호 직접 조회에 v000101 등의 번호 입력 후 Enter |
| 설정 변경 | 설정·연결 수·배정은 실행 중 고정. 다른 조건은 새 계획/실행 사용 |

운영 계획은 운행 목록을 순차로 읽어 합계와 요청한 페이지만 만듭니다. Trip 번호 중복 검사에는 자동 삭제되는 임시 SQLite 색인을 사용하며 메시지를 저장하지 않습니다. 한 번 계산한 저장 요약은 화면을 다시 열거나 실행할 때 재사용합니다. 최대 규모의 첫 합계 계산에는 시간이 필요할 수 있습니다. 차량 번호를 지정한 운영 조회는 `summary_scope=selected_vehicle`이며 합계는 해당 차량 기준, `fleet_vehicle_count`는 전체 명부 수입니다.

운영 실행은 미래 메시지가 버퍼를 채워 먼저 보낼 차량을 막지 않도록 현재 시각의 메시지를 순차 요청합니다. 마지막 Microtrip과 그보다 늦은 종료 Trip은 따로 요청하되 원래 시각과 본문을 유지합니다. 생성 버퍼 제한은 전체 프로세스 메모리 제한이 아닙니다. 명부·현재 상태·진행 색인과 Go 내부 캐시는 별도 메모리를 사용합니다.

실제 MQTT에는 서버 파일의 운영 프로필이 필요합니다. `configs/mqtt.operations.example.json`을 별도 비공개 경로에 복사하고 접속 주소·인증서·토픽·실제 계정 할당량을 확인해 설정하세요. 예제는 `enabled=false`, `contract_reviewed=false`로 비활성 상태입니다. 기존 소량 프로필을 자동 변경하지 않습니다. 서버에 운영 프로필이 설정되어 있어도 소량 시험 호출에는20연결·100건·30초·접속5회/초·발행70건/초 제한을 추가 적용합니다.

- `execution_profile=operations`: Python 제어기와 Go 송신기의 운영 범위를 함께 사용합니다.
- `connect_per_second=1000`: 한 송신 Worker의 신규 접속·재시도 합계 상한입니다. 현재 단일 실행 구조의 전체 상한이며 여러 서버의 자동 공유 제한은 아닙니다.
- `max_connecting=100`: 인증·접속 응답을 동시에 기다릴 수 있는 수입니다. 속도 상한과 별개입니다.
- `publish_per_second=15000`: 예제의 전체 발행 상한입니다. 실제 계정의 잔여 할당량에 맞춰 변경합니다. 이 처리량을 달성한다는 보장이 아닙니다.
- 운영 송신은 Client별 접속 간격1초·발행 간격10ms 이상을 적용합니다. 재접속에는 증가하는 대기와 무작위 분산을 추가합니다. Client별 미확인 메시지1개와 본문 순서는 유지합니다.
- 예제 `max_duration_seconds=2592600`은30일+종료 여유10분입니다. 실제 실행의 시간 제한은 요청 기간+10분과 서버 상한 중 작은 값입니다. 일시정지 시간도 벽시계 제한에 포함합니다.
- `max_messages`는 실제 발행 시도의 서버 상한입니다. 기본 주기보다 빠른 설정을 고려해 프로필 계약은1조 건까지 허용하지만 예제 값은 실측 용량·필수 예산이 아닙니다. 필요 실행량에 맞춰 낮춰 사용하세요.

운영 경로의 중단은 정리를 기다린 뒤 최대15초 후 남은 Worker를 강제 종료합니다. 서버 재시작 후 중단 위치부터 자동 송신을 이어가는 기능은 제공하지 않습니다. 가상시간 생성 확인은 실제30일 기다림을 생략하지만 모든 메시지를 계산하므로 건수가 많으면 상당한 시간이 필요합니다. 필요하면 실행 중단을 사용하세요.

### 이번 실행의 발행 지연 목표

실행 결과의 연결 배정과 성능에서 P95·P99 추정 상한과 실제 임계값별 건수를 확인할 수 있습니다.

- 발행 지연은 예정 시각부터 MQTT 발행 호출 직전까지입니다. 생성·대기열·접속 대기를 포함하고 일시정지 시간은 제외합니다. PUBACK 확인 대기와 구분합니다.
- 1초 이내 발행이95% 이상이고2초 이내 발행이99% 이상이면 지연 목표 충족입니다. 경계값1초·2초는 이내 건수에 포함하며5초 초과 건수는 별도로 표시합니다.
- 초기 접속·재접속을 포함한 전체 실행 기준입니다. 정상 운행 구간만 분리한 결과나 여러 서버의 통합 운영 인증은 아닙니다.
- 계획·생성·발행 시도·발행 확인·PUBACK·지연 표본 수가 일치하고 정상 완료/종료 정리가 확인되어야 목표를 판정합니다. 중단·실패·미전송·응답 미확인은 판정 보류, 실행 중은 실행 중, 송신 없는 실행은 송신 없음으로 표시합니다.
- P95·P99 상한은1µs부터2배 간격인 고정 버킷의 상한입니다. 예를 들어 P95 상한이1,048.576ms여도 실제1초 이내 건수가95% 이상이면 목표를 충족할 수 있습니다. 목표 판정에 추정 상한을 그대로 사용하지 않습니다.
- 원본 메시지별 시간열을 추가 저장하지 않고 고정 크기 히스토그램·임계값별 건수·누적 평균을 보관합니다. 이전 실행 기록의 누락된 계측값은0으로 보충하거나 통과 처리하지 않습니다.

새 결과의 `performance` 안 각 시간 항목에는 `p99_upper_ms`, `within_1s_count`, `within_2s_count`, `over_5s_count`가 추가됩니다. `transmission_goal`은 이번 실행의 목표 판정이며 MQTT로 전송하는 OBD 본문에는 들어가지 않습니다. 이 결과만으로25,000대 처리 용량이나30일 안정성을 보장하지 않습니다.

## 실행

Python 3.14 이상, Go 1.26 이상, Node.js 24.22 이상을 준비합니다.

```powershell
python scripts/dev.py prepare
python scripts/dev.py run
```

화면: http://127.0.0.1:8080

이미 설치된 환경은 run만 실행합니다. 변경 후 빌드는 `python scripts/dev.py build`, 필수 기능 확인은 `python scripts/dev.py test`입니다. 서버 재시작이 필요합니다. npm이 없으면 prepare가 npm 12.2.2를 프로젝트 내부에 준비합니다. 패키지 버전은 lock 파일로 고정합니다.

## 송신 없는 확인

기본값입니다. 차량 3대·풀 Client 2개·차량당 2건으로 입력·배정 확인 후 생성 실행 시작을 누릅니다. 차량별 JSON 6건과 고정 배정표를 확인합니다. 차량별 전체 연결은 Client 수가 차량 수와 같습니다. 실제 접속·발행·PUBACK는 0입니다. 실행 시간에서 실제 시간(주기에 맞춰 실행) 또는 가상시간(즉시 생성)을 선택합니다. 화면 기본값은 실제 시간입니다.

## 자동 주행 생성

데이터 생성 방식을 자동 주행 생성으로 바꾸고 운행 프로필·시간·생성 주기·seed·시작 시각·좌표·초기 총 주행거리를 설정합니다. 입력·배정 확인은 첫 Microtrip JSON과 예정량을 보여주며 저장하지 않습니다. 생성 실행 시작을 누르면 선택한 실행 시간에 따라 생성하고 실행 기록을 저장합니다. 결과에서 첫 차량의 속도 그래프·상태·누적거리와 차량별 종료 Trip을 확인합니다.

기본 3대·60초·2초 주기는 차량당 Microtrip 31건(t=0과 t=60 포함) + Trip 1건, 총 96건입니다. 자동 모드의 차량당 생성 건수는 운행시간과 주기로 계산하며 직접 수정하지 않습니다. 주기는 100ms 이상, 운행시간을 나누어 떨어지게 하며 최소 10구간이 필요합니다. 운행시간은 10~3,600초, 전체 메시지는 Trip 포함 10,000건까지입니다. configs/automatic.example.json은 API 요청 예시입니다.

이전 모델 combustion-demo-1은 내연기관 차량별 운행 한 회의 개발용 근사 모델입니다. 웜업/공회전 → 가속 → 정속 → 감속 → 정차/공회전 → 가속 → 정속 → 감속 → 시동 OFF 순서입니다. 도심·고속·정체는 같은 상태 순서에서 기준 최고속도(50/95/20km/h)를 바꿉니다. 실제 교통 상황이나 도로망은 재현하지 않습니다. 짧은 운행은 가속도 상한으로 최고속도가 낮아집니다.

- 고정 seed와 차량 번호로 속도 편차를 만들고 모델 버전·설정을 실행 기록에 보관합니다. 같은 설정·seed·시각에서는 같은 생성값을 얻습니다. 실제 네트워크 도착 시각의 재현을 뜻하지 않습니다.
- 속도는 구간별 선형 변화, 가속도는 최대 2m/s²입니다. 거리와 연료는 상태 구간을 적분해 계산하므로 보고 주기만 바꾸어도 종료 집계는 같습니다. 위치는 가상 시작점에서 동쪽 방향 대권 경로로 계산하며 실제 도로 경로가 아닙니다.
- RPM·부하·스로틀은 속도와 가속/감속 상태에 연동합니다. Trip의 거리·평균/최고속도·공회전·웜업·연료차단 시간은 같은 모델에서 집계합니다. 총 주행거리는 초기 총 주행거리 + 이번 운행거리입니다.
- 개발 단위: sp/hsts/mesp km/h, 거리 m, fc 누적 L, coe g, ctp ℃, fct/idt/wut/dtvt 초, ts/stt/edt/clt UTC 밀리초입니다. 일부 단위·배율은 원문에서 미확정이며 수신 호환성을 보장하지 않습니다.
- 연료는 감속 구간을 연료차단으로 가정하고 나머지 시간에 0.8L/h + 7L/100km의 거리 항을 적용합니다. 탄소는 2,310g/L의 고정 계수, 냉각수는 25→90℃/180초 상승으로 가정합니다. 모두 실차 보정 전 모델 상수이며 측정값이 아닙니다. vv/btv는 시동 OFF 후 배터리 전압 12.6V, gnv는 주행 최고 발전기 전압 14.2V의 가상값입니다. 표현이 불명확한 em/xyz는 자동 발행하지 않습니다.

자동 모드도 기존 풀/차량별 연결 엔진을 사용합니다. 마지막 Microtrip과 Trip은 같은 운행 종료 시각으로 생성하고 순서대로 발행합니다. Trip도 건수·속도 상한에 포함합니다. 실제 MQTT 시험은 운행시간이 서버 전체 제한시간보다 짧아야 하며 접속·응답 시간 여유가 필요합니다. 기본 60초 자동 예시는 현재 MQTT 최대 30초 상한을 넘으므로 송신 없는 확인용입니다. 다중 운행·주차 간격·차량별 출발 시각 분산은 후속입니다.

## 이전 상황 기반 운행 모델 v2

combustion-scenario-2는 이전 API 요청과 실행 기록 조회를 위해 유지합니다. 새 화면에서는 선택하지 않습니다. 새 화면과 configs/automatic.example.json은 v6를 명시합니다. 버전 없는 API 요청은 combustion-demo-1로 해석해 호환합니다. 저장된 운행 설정을 새 모델로 자동 재해석하지 않습니다.

v2는 운행시간의 고정 비율 대신 절대 시간의 가감속·정속·정차 구간을 반복합니다. 운행시간을 늘리면 상태가 더 반복되며 가속 시간을 비례해 늘리지 않습니다. 정상 가속은 운전자 성향에 따라 0.8/1.2/1.6m/s², 감속은 1.5m/s²를 기준으로 하고 젖은 노면은 이를 줄입니다. 종료 전 감속 여유를 두고 마지막에 시동 OFF를 표시합니다. 모두 실차 보정 전 개발 가정입니다.

| 상황 | v2 반영 방식 |
|---|---|
| 골목·보호/주의·도심·간선·고속 도로 | 가상 도로 유형별 속도 기준과 차량별 선호 속도 적용. 기준20/30/50/70/100km/h는 법정 제한속도 데이터가 아닌 시나리오 상수 |
| 혼잡·앞차 | 목표 속도 감소·유지 및 정체 정차. 실제 다른 차량의 위치/차간거리 추종은 아님 |
| 신호·잠시 볼일 | 감속 후 속도0·엔진 공회전으로 대기, 이후 재출발. 엔진 OFF/주차와 구분 |
| 커브·회전·저속 유턴 | 회전 반경과 속도에서 방향/위치/횡가속을 함께 계산. 정상 회전은 1.2m/s² 이하의 개발 기준 |
| 오르막·내리막 | ±5% 이내 가상 경사로 목표 속도 일부·엔진 부하·연료를 조정. 고도 필드는 전송하지 않음 |
| 운전자·노면 | 신중/보통/적극의 가속 차이, 선호 속도 편차, 차량별 가상 건조/젖은 조건. 실제 공간·기상 공유 모델은 없음 |
| 다차선·1차선 | 차로 수만으로 속도를 결정하는 규칙은 제외. 속도 기준·교통 조건으로 표현 |
| 급박한 사정 | 실제 사정을 추정하지 않으며 적극 성향 또는 명시적 이상 대상으로만 표현. 자동 과속 규칙은 없음 |

시나리오의 위치는 시작점 주변 평면 근사 경로입니다. 직선·곡선 구간을 연속 연결하고 속도를 적분한 거리와 연결합니다. 실제 도로망·신호 제어·차량 간 상호작용·차선 변경·실차 엔진/연료 정밀 모델·센서 잡음은 미구현입니다. EPA 자료를 가져와 보정한 모델도 아니며 특정 지역의 교통 분포를 대표하지 않습니다.

### 이상 대상 차량과 실제 이벤트

anomaly_vehicle_percent(0~100)는 전체 차량 수에 곱해 반올림한 수만큼 seed 기반으로 선정합니다. 예를 들어 3대의50%는2대이며 작은 차량 수에서는 비율 해상도가 거칩니다. 정상 차량에는 내부 이상 이벤트를 지정하지 않습니다. 선정 난수와 주행 상황/이벤트 난수 흐름을 구분하며 같은 설정·seed·모델로 재현합니다.

anomaly_events_per_hour(0~60)는 대상 차량의 확률적 기준 빈도입니다. 현재는 상황 선택 구간마다 기준35초에 해당하는 빈도 비율을 발생 확률로 적용합니다. 구간 길이와 운행 조건이 달라 실제 시간당 발생 횟수는 이 수와 다를 수 있습니다. 이는 정확한 이벤트 할당량이 아닙니다. 이벤트 종류는 급가속(3.3m/s²)·급감속(3.8m/s²)·급회전(가능한 반경/속도에서 횡가속3m/s² 이상)이며 조건이 맞지 않으면 지정 후보라도 실제 이벤트로 집계하지 않습니다. 정상 차량의 가감속/회전 한도는 더 낮습니다. 임계값은 개발 기준이며 법적/보험 기준으로 쓰지 않습니다.

결과는 선정 대상 차량 수·실제 발생 차량 수·이벤트 구간 수를 구분합니다. 이벤트 구간 수는 메시지 수가 아니며 같은 이벤트가 여러 Microtrip에 걸쳐도 구간 기준으로 셉니다. 짧은 운행·낮은 빈도에서는 대상 차량에도 이벤트가 없을 수 있습니다. 기준 비율을 맞추기 위해 모든 대상에 억지로 이벤트를 발생시키지는 않습니다.

이벤트·도로·사유·운전자·노면·경사·가속/횡가속은 실행 결과의 내부 context로 표시하며 MQTT 메시지 본문에는 추가하지 않습니다. em/xyz의 미확정 단위/표현을 임의로 확정하거나 자동 발행하지 않습니다. 시드/부동소수 계산을 보존해 같은 버전 내 주행과 Trip 집계를 재현합니다.

### 차량별 구간 조회

결과에서 차량 번호와 시작·종료 경과초를 설정한 뒤 선택 차량 조회를 누릅니다. 종료를 비우면 해당 차량의 생성 구간 끝까지 조회합니다. GET /api/runs/{id}/trace/{vehicle_number}?start_seconds=100&end_seconds=200으로도 조회할 수 있습니다.

조회는 저장 설정·seed·모델 버전으로 구간을 재생성하며 전송/브로커 수신 증빙이 아닙니다. 부분 실행에서는 차량별 실제 생성 순번을 계산해 미래 구간 조회를 차단합니다. 모델 버전이 없는 이전 결과는 v1로 조회합니다. 한 번에 최대120점만 반환하므로 전체1시간 그래프에서는 짧은 정차/이벤트가 생략될 수 있습니다. 구간을 좁히면 설정 보고 주기에 맞춰 더 자세히 볼 수 있습니다. 보고 주기보다 짧은 사건의 정밀 분석은 현재 범위 밖입니다.

전체 차량 시계열을 DB에 추가 저장하지 않으며 기존 첫 차량 trace120점·Trip100대·샘플10건 제한을 유지합니다. 현재 단일 Worker의 합성 모델이며 대규모 용량 측정은 아직 없습니다.

## 실제 TLS MQTT 소량 시험

1. configs/mqtt.example.json을 .local/mqtt.json으로 복사합니다.
2. 시험 대상의 데이터 endpoint를 ssl://호스트:포트로 설정합니다. AWS X.509 MQTT는 기본 8883을 사용합니다.
3. CA·인증서·개인 키를 certs 또는 .local에 보관하고 파일 경로를 설정합니다. 상대 경로는 프로젝트 루트 기준입니다. 파일 자체를 저장소에 올리지 않습니다.
4. 수신 규격·토픽·접속 권한을 확인한 뒤 서버 파일의 enabled와 contract_reviewed를 true로 변경합니다.
5. 시험 상한을 정하고 서버를 실행합니다. 화면에서 실제 MQTT 송신과 송신 확인을 선택한 뒤 MQTT 실행 시작을 누릅니다.

프로필 경로는 서버 환경변수 DANGUBI_MQTT_PROFILE로 바꿀 수 있습니다. 브라우저에서는 접속 주소·인증서·개인 키를 설정하거나 열람할 수 없습니다. 요청·실행 기록에도 접속 프로필은 넣지 않습니다.

설정한 topic_prefix가 sim일 때 토픽은 sim/{run_id}/{vehicle_id}/obd입니다. Client ID는 sim-{run_id}-c{연결번호}입니다. 해당 형식의 접속과 차량별 토픽 발행이 허용된 정책이 필요합니다. 현재 한 실행에서는 같은 인증서를 사용하므로 차량별 독립 인증서 시험과는 다릅니다.

프로필 기본 상한: Client 5개, 발행 20건, 전체 30초, 접속 2개/초, 발행 10건/초, 응답 대기 3초, 접속 재시도 2회입니다. 이 단계의 코드상 최대값은 Client 20개·100건·30초·접속 5개/초·발행 70건/초·접속 재시도 3회입니다. 대규모 시험 도구로 해석하지 않습니다.

## 기존 소량 시험의 실제 전송 동작

- 풀과 차량별 전체 연결 모두 실행 전 배정표를 고정합니다. 실행 중 증감·재배정은 지원하지 않습니다.
- 기간 내내 유지는 시작 시 연결하고 실행 종료 시 모두 해제합니다. 주차 상태까지 포함한 장시간 유지는 아직 없습니다.
- 운행 중 유지는 해당 Client의 첫 메시지에서 연결하고 마지막 메시지 PUBACK 뒤 해제합니다. 수동 모드는 입력 구간을 한 운행으로 간주하고, 자동 모드는 웜업부터 종료 Trip 응답까지 유지합니다. 정차 중에는 해제하지 않습니다. 다중 운행은 후속입니다.
- TLS 1.2 이상, CA·서버 이름·클라이언트 인증서를 검증합니다. 인증서 검증 우회와 암호화 없는 tcp 연결은 지원하지 않습니다. 443/ALPN·WSS는 아직 지원하지 않습니다.
- QoS 1, retain=false로 발행합니다. 생성 주기와 전체 발행 속도를 함께 제한하므로 실제 간격은 더 길어질 수 있습니다.
- 끊긴 연결은 동일 Client ID로 제한된 횟수만 재접속합니다. 발행 응답이 없으면 중복 가능성이 있어 자동 재발행하지 않고 미확인으로 기록한 뒤 중지합니다.
- 접속 확인 Client는 접속 성공을 확인한 고유 Client 수입니다. MQTT 발행·PUBACK는 응답 확인 건수입니다. 발행 시도·응답 미확인·재연결 시도를 별도 표시합니다. 종료 시 연결을 정리합니다.
- 실패·부분 완료를 완료와 구분합니다. PUBACK는 브로커 확인이며 저장소 도착이나 파이프라인 검증이 아닙니다.

## 입력과 실행 기록

contracts/obd-development.json의 개발용 잠정 규격으로 입력 항목과 서버 검증을 공유합니다. ty=4 Microtrip, ty=3 Trip이며 실제 수신 규격과의 호환성은 확인이 필요합니다. 문서에서 불명확한 단위·자료형은 화면에 표시합니다.

수동 모드는 입력값을 차량별로 복제하고 tid와 시각을 갱신합니다. 자동 모드는 운행 설정으로 두 종류의 메시지를 생성합니다. 송신 없는 확인은 최대 10,000건입니다.

실행 설정·수동 입력 또는 자동 생성 설정·처리/전송 집계·최대 100대 배정표·메시지 샘플 10건을 .local/runs.sqlite3에 저장합니다. 자동 모드는 추가로 생성된 종료 Trip JSON 최대 100대와 첫 차량 변화 최대 120점을 저장합니다. 전체 원본 메시지는 저장하지 않으며 나머지는 생성·집계/전송 후 버립니다. 생성 요약은 생성된 구간 기준이며 전송 성공 건수와 별개입니다. 전체 계획·생성·미생성·발행 미시도·응답 미확인·PUBACK를 구분합니다.

최근 실행은 최신 30개를 조회하지만 DB의 오래된 실행을 자동 삭제하지는 않습니다. 입력·배정 확인만 한 결과는 DB에 저장하지 않습니다. DB 위치는 서버 환경변수 DANGUBI_DB로 변경할 수 있습니다. 운영 저장소는 미확정입니다. PATCH 요청으로 저장된 실행 설정을 바꿀 수 없습니다. .local과 실행 데이터는 GitHub에 포함하지 않습니다. AWS IoT Core 이후 저장은 이 제품의 검증 범위에 포함하지 않습니다.

## 실행 시작·조회·중단

화면의 생성 실행 시작 / MQTT 실행 시작은 비동기 실행입니다. 실행 ID를 바로 받은 뒤 진행 상태를 주기적으로 조회합니다. 첫 구현은 단일 API 프로세스에서 한 번에 한 실행만 허용합니다. 실행 중에는 설정을 바꾸지 못하며 상단 실행 중단 버튼으로 중단할 수 있습니다. 새로고침하면 진행 중인 실행 ID와 고정 설정·상태를 다시 불러옵니다. 브라우저를 닫아도 실행 자체는 계속됩니다.

- 실제 시간: 설정한 주기로 생성합니다. 송신 없는 실제 시간 실행은 최대 3,600초이고 전체 생성 상한 10,000건을 유지합니다. MQTT는 기존 최대 30초·100건·Client 20개 상한과 서버 설정을 그대로 적용합니다.
- 가상시간: 송신 없이 시각만 증가시켜 즉시 생성합니다. 실제 MQTT는 항상 실제 시간으로 동작합니다. 입력·배정 확인은 시간 대기 없이 미리보기만 만듭니다.
- 중단은 새 생성을 멈추고 Worker가 MQTT 연결을 정리하도록 요청합니다. PUBACK 대기 중이던 메시지는 응답 미확인으로 남을 수 있습니다. 중단된 운행의 종료 Trip은 임의로 새로 만들지 않습니다.
- 중단 응답이 2초 안에 돌아오지 않으면 Worker를 강제 종료하고 최종 전송·연결 정리를 미확인으로 표시합니다. 실행시간 제한 초과는 실패로 보관합니다. API 정상 종료 때도 진행 중인 Worker를 정리합니다.
- API 재시작 시 이전의 실행 중 기록은 interrupted(종료 미확인)로 표시하고 자동 재실행하지 않습니다. API와 Worker 사이 입력 연결이 끊기면 Worker도 중단합니다. 이는 체크포인트 복구나 분산 소유권 관리가 아닙니다.
- 시작 시부터 같은 SQLite 실행 기록을 갱신하며, 진행 스냅샷을 계속 쌓는 별도 테이블은 만들지 않습니다. 샘플/요약 상한도 유지합니다. 메시지는 순차 생성·처리해 무제한 전송 대기열을 만들지 않습니다. 지연이 생기면 주기 지연 지표로 표시하며 목표 TPS 달성을 보장하지 않습니다.

## 일시중지·재개

실행 중 상단의 일시중지를 누르면 pausing(일시중지 요청 중)으로 전환합니다. Worker가 이미 시작한 접속·발행 응답을 기존 제한시간 안에서 처리하고, 다음 생성/발행 경계에서 paused(일시중지됨)를 보고합니다. 요청 직후와 정지 완료를 구분하며, 응답이 오지 않은 발행은 기존 방식대로 실패·미확인으로 처리합니다.

- 일시중지 완료 뒤에는 새 데이터 생성·접속·발행을 하지 않습니다. Paho의 MQTT keepalive는 계속 동작하며 기존 연결을 유지합니다. 네트워크가 끊어졌다면 재개 뒤 기존 고정 Client ID로 제한된 재접속을 시도합니다. 일시중지를 이유로 차량 배정이나 Client ID를 바꾸지 않습니다.
- 실행 재개를 누르면 resuming(재개 요청 중)을 거쳐 running으로 돌아갑니다. 정지 시간만큼 생성 예약 기준을 이동해 남은 간격부터 이어가므로 정지 중의 메시지를 추가 생성하거나 몰아서 보내지 않습니다. 차량별 순번·가상 시각·seed·누적값은 이어집니다.
- 화면은 실제 경과시간, 정지시간, 정지를 제외한 실행시간, 운행 진행시간을 구분합니다. 운행 진행은 마지막 생성 메시지의 가상 경과시간입니다. 설정된 전체 제한시간은 정지 중에도 계속 적용됩니다. dry_run 실제 시간 실행은 원래 예정 시간+10초, 가상시간은 30초, MQTT는 서버의 기존 최대 30초입니다. 정지 때문에 한도를 넘으면 실패/부분 결과로 종료하며 한도를 자동 연장하지 않습니다.
- 정지 중에도 실행 중단과 서버 정상 종료 처리가 가능합니다. 브라우저 새로고침은 같은 paused 실행과 고정 설정을 복원합니다. 정지된 실행도 단일 실행 자리를 점유합니다. 완료·중단·실패한 실행을 재개하거나 다른 실행으로 복제하는 기능은 아닙니다.
- 같은 일시중지 또는 재개 요청의 반복은 상태를 다시 뒤집지 않습니다. 일시중지 요청과 완료, 재개 요청과 완료 사이에는 잠시 대기할 수 있습니다. 빠른 가상시간 실행은 제어 요청 전에 이미 완료될 수 있습니다.

API:

| 요청 | 결과 |
|---|---|
| POST /api/jobs | 202와 실행 ID·고정 요청·초기 상태 |
| GET /api/jobs/{id} | 진행 중/최종 실행 기록 |
| POST /api/jobs/{id}/pause, /resume | 일시중지/재개 요청. Worker 확인 후 상태 전환 |
| POST /api/jobs/{id}/stop | 중단 요청. 완료된 실행에 반복해도 결과를 바꾸지 않음 |
| GET /api/runs, /api/runs/{id} | 기존·신규 실행 기록 조회 |
| POST /api/preview | 송신·저장 없는 입력/배정 확인 |

POST /api/runs의 기존 완료 대기 방식은 호환용으로 유지합니다. realtime=true 실행은 /api/jobs를 사용해야 합니다. API 요청 예시는 configs/automatic.example.json이며 realtime을 true로 지정하면 실제 시간 생성이 됩니다. 실제 MQTT와 호환용 MQTT 실행은 동일 잠금을 사용해 겹치지 않게 합니다. 현재 여러 API 프로세스나 서로 다른 서버 사이의 중복 실행은 방지하지 못하므로 하나의 서버 프로세스만 실행합니다.

상태는 starting/running/pausing/paused/resuming/stopping/completed/stopped/failed/interrupted로 구분합니다. Worker 처리 상태와 job_state(실행 관리 상태)를 함께 저장합니다. 일반적인 Worker 정상 응답을 받은 경우에만 연결 정리 확인됨으로 표시합니다. 강제 종료나 서버 비정상 종료의 마지막 숫자를 확정된 최종 상태로 해석하지 않습니다.

## 검증과 운영 범위

Go 테스트는 상태 전환·거리 적분·Trip 집계·seed 재현·보고 주기 독립성·표시용 기록 상한을 검사합니다. 로컬 TLS 전송에서 자동 Microtrip과 마지막 Trip의 발행·응답도 확인합니다. Go 테스트에서 임시 CA·인증서와 로컬 상호 TLS 브로커를 생성해 풀/전용 연결·PUBACK·동일 ID 재연결·응답 없음·잘못된 CA·시험 제한시간을 검사합니다. API 테스트는 입력 오류·고정 설정·서버 프로필 및 송신 확인·실제 송신 상한을 검사합니다. 테스트 인증 자료는 임시 디렉터리에서만 생성합니다. 실행 관리 시험은 시작 응답·실행 중 조회·고정 기록·중단/반복 중단·정상 종료·강제 종료·제한시간·재시작 기록 복구·서버 종료 정리와 실제 로컬 TLS MQTT 연결 중 중단을 확인합니다. 일시중지 시험은 남은 주기·데이터/Trip/seed/배정 보존, 정지 중 생성·발행 고정, 전체 제한시간, 서버 종료, 실제 TLS 연결 유지와 재개를 검사합니다.

현재는 127.0.0.1에 바인딩하는 단일 로컬 API 프로세스입니다. 비동기 실행은 프로세스 내 한 번에 하나만 허용합니다. 다중 API 프로세스·공개 서비스·분산 실행에는 별도 인증·실행 관리가 필요합니다. 다중 운행·출발 분산, 목표 TPS/부하 패턴, CPU·메모리 측정, 장시간 부하와 자동 확장은 후속입니다. 현재 단계는 시작·조회·일시중지·재개·중단 기반이며 대규모 실행 완료를 뜻하지 않습니다.

AWS 실제 연동은 endpoint·토픽·인증서·정책 확인 후 시행해야 합니다. AWS 운영 실행 환경은 별도 선택합니다.

공식 자료: [AWS 통신·인증](https://docs.aws.amazon.com/iot/latest/developerguide/protocols.html), [AWS MQTT](https://docs.aws.amazon.com/iot/latest/developerguide/mqtt.html), [Eclipse Paho Go](https://github.com/eclipse-paho/paho.mqtt.golang).

자동 생성 규격 근거: [Smart Fleet 메시지 7.2.2 OBD](https://smart-fleet-docs.readthedocs.io/ko/latest/message/#obd). 원문은 필드 의미의 근거이며 생성 모델 상수의 근거는 아닙니다.

## 실행 기록 정리와 결과 읽기

최근 실행의 체크박스로 종료 기록을 선택하고 선택 기록 삭제를 누릅니다. 확인 화면에 표시된 실행 ID와 개수를 검토한 뒤 영구 삭제 확인을 누르면 해당 SQLite 기록의 설정·집계·샘플·Trip·그래프를 함께 삭제합니다. 실행 중/일시중지 기록은 삭제할 수 없으며 먼저 중단해야 합니다. 표시된 종료 기록 선택은 현재 표시된 최대 30개 중 종료 기록만 선택합니다. 삭제 후 새로 목록을 조회해 이전 기록을 추가 정리할 수 있습니다. 자동 삭제나 AWS 데이터 삭제는 하지 않습니다. SQLite 파일 크기는 즉시 줄지 않을 수 있으며 비워진 공간을 이후 기록에 재사용합니다.

연결·생성 설정과 처리 결과 옆의 동그란 i 버튼은 마우스를 올리거나 키보드로 초점을 주면 설명을 표시합니다. MQTT 발행은 현재 구현에서 PUBACK까지 확인한 건수이므로 PUBACK 수와 같은 기준입니다. 후속 저장 완료를 의미하지 않습니다.

생성 메시지 보기와 Trip JSON 보기 안에서 표로 보기/JSON으로 보기를 전환합니다. 표에는 개발 JSON Schema의 한국어 항목명·원문 필드·값을 표시하고 시각은 서울 시간과 원래 UTC 밀리초를 함께 표시합니다. 숫자는 소수 최대 6자리로 표시하며 원본 JSON은 보존합니다. 정의되지 않은 단위나 필드를 확정된 값처럼 바꾸지 않습니다. 이 전환은 표시 방식만 변경하며 전송 JSON을 수정하지 않습니다.


## 이전 경로 기반 v3: 도로와 상황의 관계

새 화면과 예제는 v4를 사용합니다. `combustion-route-3` 및 v1/v2는 그대로 선택할 수 있고 저장 기록도 원래 버전으로 재생성합니다. 버전이 없는 API 요청은 기존처럼 v1입니다.

v3는 먼저 합성 경로를 정하고 그 안에서 교통 상태·가감속·정차·회전을 생성합니다. 실제 대한민국 지도나 실시간 교통정보를 수입한 결과가 아닙니다. 아래 시간·속도·확률은 개발 가정이며 한국 도로의 대표 통계나 법정 속도 규칙이 아닙니다.

| 관계 | 현재 생성 규칙 |
|---|---|
| 고속 중심 경로 | 도심 → 간선 → 진입로 → 고속 → 진출로 → 간선 → 도심. 진입·진출은 화면에서 `진출입로`로 표시 |
| 고속 구간 유지 | 900초 이상인 고속 프로필은 양쪽 접근·진출 구간을 제외한 시간을 하나의 고속 구간으로 유지. 접근/도착 각각30~60초, 간선 각각40~90초, 진출입로 각각100~150초. 1시간이면 고속 구간3000~3260초 |
| 혼합 경로 | 900초 이상에서 차량 seed에 따라55% 후보 확률로 위 고속 경로를 선택. 나머지는 일반도로 경로. 900초 미만은 고속 프로필도 일반도로 경로만 생성 |
| 일반도로 연결 | 도심↔간선 또는 도심↔골목. 각 기본 구간120~420초. 골목과 간선이 직접 바뀌지 않음 |
| 보호구역 | 일반도로 경로의 도심 구간 일부에만20~60초 제한을 추가. 조건을 만족하는 도심 구간에서20% 후보 확률, 이전 보호구역 종료 후600초 이상. 한국 실제 노출률이 아니며 사용자가 조정하는 설정도 아님. 고속 경로 템플릿의 접근·도착에는 현재 미배치 |
| 교통 상태 | 원활/앞차/혼잡 상태를90~300초 유지. 같은 상황 안에서 작은 속도 편차 적용. 혼잡은 고속에서도 정체 정차로 이어질 수 있음 |
| 정차·회전 | 고속 본선에는 신호 대기·볼일 정차·유턴·교차로 회전 없음. 진출입로에는 정차 후보를 만들지 않음. 저속 유턴은 도심/골목에만 허용. 급회전 후보도 고속 본선에서 제외 |
| 진입과 경계 | 낮은 속도 구간이60초 안에 있으면 감속 목표에 반영. 경계에서 구간을 잘라 속도·거리·좌표를 연속 적분. 감속 진입 중 표시 속도 상한은 이전 속도까지 포함하므로 그 값을 해당 도로의 법정 제한속도로 해석하면 안 됨 |

이상 대상 선정·35초 기준 후보 확률 및 조건 충족 이벤트 집계는 v2 방식을 유지합니다. 실제 시간당 발생량 보장이나 실차 보정은 아닙니다. 도로/교통/이벤트 차이로 같은 빈도 설정에서도 실제 발생량이 달라집니다. 운전자 성향·노면은 차량의 해당 운행 동안 유지합니다. 차량 간 같은 위치의 날씨·정체 공유는 구현하지 않았습니다.

아직 없는 관계: 실제 출발지/목적지 기반 길찾기, 일방통행·회전 금지, 도시고속도로/일반국도/지방도 구분, 교차로별 신호 주기, 앞차 추종·차로 변경, 휴게소·통행료 처리, 공간적으로 연결된 커브/경사, 주차 후 재출발, 공유 기상, 시간대별 출퇴근, 현재 사고/공사의 발생·해소입니다. 사고다발지역을 실제 사고 또는 자동 이상 이벤트로 해석하지 않습니다. 보호구역 위치 점을 경계 영역 전체로 해석하지 않습니다. 가상 좌표는 실제 도로 위에 놓인다고 보장하지 않습니다.

## 그래프 구간 선택과 Microtrip 조회

차량별 속도 그래프의 그리기 영역을 좌우로 드래그하면 해당 구간으로 확대하고, 같은 차량·구간의 상황표와 Microtrip을 조회합니다. 반대 방향으로 드래그해도 같습니다. 짧은 클릭·드래그 취소는 조회하지 않습니다. 시작/종료 입력과 선택 차량 조회 버튼은 키보드로도 사용할 수 있습니다. 전체 생성 구간 보기로 해당 차량의 현재 생성 완료 구간으로 돌아갑니다. 실행 중 기본 그래프의 진행 표시는 유지하며, 사용자가 조회한 구간은 그 시점의 고정 결과입니다. 새 데이터를 포함하려면 다시 조회합니다.

선택 구간 Microtrip은 원래 생성 주기의 메시지입니다. 그래프는 계속 최대120점 요약이지만 메시지는 생략하지 않고 페이지당100건의 이전/다음 조회로 확인합니다. 시작·종료 시각을 포함하되 해당 범위에 실제 생성 시점이 없는 경우0건입니다. 페이지를 넘길 때 조회 완료 시각을 고정해 실행 중 생성량이 늘어도 같은 범위를 유지합니다. 조회 차량의 생성 완료 시각 이후는 조회할 수 없습니다. 조회 범위를 바꿔도 종료 Trip은 전체 운행 요약으로 유지하며 구간 Trip을 새로 만들지 않습니다.

API `GET /api/runs/{run_id}/trace/{vehicle_number}?start_seconds=100&end_seconds=420&message_offset=0`은 trace와 samples, message_total, message_offset, range_end_seconds를 반환합니다. message_offset은0~10000, 반환 메시지는 최대100건이며 종료 Trip(ty3)은 제외합니다. 자동 생성 기록만 지원하고 v1/v2/v3의 저장 모델 버전을 사용합니다. 조회는 설정·seed로 재생성하는 읽기 작업이며 전체 메시지를 DB에 추가 저장하거나 MQTT에 다시 발행하지 않습니다. 재생성한 값은 당시 전송 원문 보관·PUBACK·AWS 수신 기록의 증거가 아닙니다. 재생성의 참고 토픽은 당시 MQTT 프로필의 발행 토픽을 보장하지 않습니다.

## 전송 OBD와 로컬 부가 정보 구분

MQTT payload에는 각 `sample.message`의 `ty`, `ts`, `pld`만 직렬화합니다. 차량/Client/토픽/순번, vehicle_state, context의 도로·상황·경사·운전자·노면·내부 이벤트, 생성 설정의 model_version/seed 등은 MQTT payload에 포함하지 않습니다. 로컬 SQLite 실행 결과의 제한 샘플·Trip에는 메시지와 부가 정보를 별도 필드로 함께 보관합니다. 경로/상황 계획 전체를 전송하거나 전체 시계열을 DB에 추가 적재하는 구조는 아닙니다. OBD 규격의 단위/표현 미확정 항목은 기존 개발 규격의 한계를 유지합니다.

표로 보기와 JSON으로 보기는 모두 OBD 메시지를 표시합니다. 여러 메시지 JSON은 확인 편의를 위해 배열로 보이지만 MQTT는 배열 전체가 아니라 각 OBD 객체를 하나씩 발행합니다. 로컬 부가 정보 보기 · MQTT 전송 제외를 별도로 열어 차량/Client/참고 토픽/상황 등을 확인할 수 있습니다. 전체 Worker 결과나 API 실행 기록 JSON 자체는 로컬 관리 자료이므로 부가 정보가 포함됩니다.


## 국내 도로 기본 규칙 v4

이전 `combustion-korea-4`는 계속 선택할 수 있으며 아래 국내 도로 규칙은 v5에도 적용합니다. 기존 v1/v2/v3/v4는 원래 결과로 재생성하며 버전 없는 API 요청의 기본 v1도 유지합니다. 사용자 화면은 데이터 생성·연결/전송·차량별 그래프와 구간 Microtrip 확인에 집중합니다. 운행 분포 분석·외국 시험 사이클 비교 화면/API는 제공하지 않습니다.

v4는 주거·상업·공업지역 일반도로를 기본 맥락으로 도심/간선의 제어 상한을50km/h로 둡니다. 고속도로100km/h는 개발용 승용차·편도2차로 이상 기본 시나리오이며 실제 노선별 표지·차종을 판독한 결과가 아닙니다. 골목20·진출입로50 등은 개발 설정이고 전국 공통 법정값이 아닙니다. 실제 표지/지정 구간, 비도시 일반도로, 자동차전용도로, 고속도로 지정 구간/차종별 속도는 별도 반영하지 않습니다.

날씨 조건은 실행 전에 건조 또는 강우·젖은 노면을 선택합니다. 기본 건조이며 같은 실행의 차량 전체에 적용하는 가상 조건입니다. 강우는 각 구간 제어 상한의80%를 사용하며 가감속도 완화합니다. 정상/이상 대상 모두 같은 제어 상한 안에서 생성합니다. 폭우·안개·결빙·적설과 가변 속도표지는 별도 모델링하지 않으며 실제 기상 조회도 아닙니다. v1/v2/v3에는 이 날씨 설정을 적용할 수 없습니다.

v4의 내부 context.speed_limit_kmh는 날씨를 반영한 제어 상한입니다. v3처럼 진입 속도를 감추려고 상한을 이전 속도까지 올리지 않습니다. 다음 저속 구간을 앞두고 감속하는지 개발 시험에서 확인합니다. 실제 경로의 유턴 허용 지점을 알 수 없으므로 v4는 유턴을 기본 생성하지 않습니다. 진출입로 회전은 교차로 회전이 아닌 커브로 표시합니다. 기존 도로 연결·구간 유지와 그래프 드래그·Microtrip 조회는 유지합니다.

근거: [현행 도로교통법 시행규칙 제19조](https://www.law.go.kr/LSW/lsLinkCommonInfo.do?lsJoLnkSeq=1020723469). 이 기본 규칙 반영은 한국 실차 운행과의 통계적 일치를 보증하지 않습니다. 가상 좌표는 실제 도로망에 맞춰져 있지 않고, 도로 길이/신호/차량 상호작용/출발 시간대·RPM·연료·냉각수·전압 등에는 개발 근사가 남아 있습니다. OBD 단위·자료형/수신 호환성 미확정 항목도 기존대로 확인이 필요합니다. MQTT에는 OBD message만 발행하며 실제 AWS 접속은 endpoint·인증서·정책을 준비한 뒤 시험합니다.

## 주행·엔진 연관 모델 v5

이전 `combustion-powertrain-5`는 계속 선택할 수 있으며 아래 엔진 연관 구조는 v6에도 적용합니다. 가솔린 승용차·6단 자동변속기의 개발용 근사이며 특정 제조사·차종의 ECU를 재현하지 않습니다. 전기차·하이브리드·디젤·CVT는 이 모델의 대상이 아닙니다. 기존 도로 연결·신호·정차·강우 규칙과 차량별 운전자/이상 대상 선정을 유지합니다.

| 상황 | 생성값의 연관 관계 |
|---|---|
| 가속·오르막 | 차량 질량·가속도·경사·구름저항·공기저항으로 필요한 차륜 출력을 계산하고 부하·스로틀·연료에 반영 |
| 변속 | 속도·기어비·타이어 크기로 RPM 목표를 계산. 부하별 변속 기준·최소 유지시간·RPM 응답 지연 적용 |
| 감속·내리막 | 온도·속도·RPM·차륜 출력 조건을 만족할 때만 연료 차단. 냉간·저속 감속은 연료 분사 유지 가능 |
| 시동 유지 정차 | 속도는 0이지만 공회전 RPM·연료 소비·충전 전압 유지 |
| 운행 종료 | RPM·부하·스로틀 0, 배터리 전압으로 전환. 마지막 Microtrip과 Trip의 누적 연료 일치 |

엔진 시작 상태는 `engine_start: cold`(기본20℃) 또는 `warm`(85℃)입니다. 냉각수는 부하에 따른 열응답으로 변하며 냉간에는 공회전 RPM과 연료가 증가합니다. 전압은 시동 후 충전 전압으로 접근합니다. 차량별 질량·정격출력·토크·공회전·전압 편차는 seed로 결정하고 실행 중 고정합니다.

모델 내부는 메시지 보고 주기와 별도로0.5초 간격으로 계산합니다. 연료 유량은 각 계산 간격에 고정해 누적하므로 보고 주기2초→4초 변경이 Trip 연료를 바꾸지 않습니다. 조회 재생성용 상태는 메모리에10초 간격으로만 보관하며 DB에 전체 시계열을 추가 저장하지 않습니다. 기존 최대120점 그래프와 구간별 Microtrip 재생성을 그대로 사용합니다.

Trip의 `fc`는 누적 연료, `fct`는 조건부 연료 차단 시간, `ctp`는 시간 가중 평균 냉각수 온도, `wut`는 냉각수70℃ 미만 시간입니다. `btv`/`gnv`는 차량별 가상 배터리/충전 기준 전압입니다. 단위는 기존 개발 기준(L/초/℃/V)이며 외부 수신 계약 확정을 의미하지 않습니다. 탄소는 기존 개발 계수2,310g/L를 유지합니다.

기어·엔진 상태·차륜 출력·연료 유량·냉각수 순간값은 로컬 `context`에만 있습니다. MQTT payload에는 기존 `ty`/`ts`/`pld`와 OBD 필드만 보내며 새 진단 필드를 넣지 않습니다. 화면 상황표의 엔진 상태·기어로 변속/냉간/온간/연료 차단을 확인할 수 있습니다.

물리적 연관 구조는 [FASTSim 공식 개요](https://natlabrockies.github.io/fastsim/getting-started/)를 참고했지만 FASTSim 자체를 실행하거나 결과로 보정하지 않았습니다. [현대자동차 자동변속기 안내](https://ownersmanual.hyundai.com/full_webhelp/CN7/2025/en_GN/id1ae50df0d75.html)는6단 자동/엔진 브레이크의 참고이며 구현 기어비의 출처가 아닙니다. [한국교통안전공단 센서 자료](https://www.data.go.kr/data/15103532/fileData.do?recommendDataYn=Y)는 대형 경유 버스여서 승용차 보정 자료로 직접 적용하지 않았습니다.

질량/기어비/효율/열응답과 연료 차단70℃·진입1500RPM/해제1200RPM·변속 최소2초 등의 수치는 개발 가정입니다. 가솔린 에너지는8.8kWh/L의 근사값이며 특정 국내 연료 측정값이 아닙니다. 최대 차륜 출력으로 가속을 제한하지만 토크 컨버터·타이어 접지·변속 중 구동력·보조 전장 부하는 완전한 동역학 모델이 아닙니다. 대한민국 실차 통계와 일치하도록 보정했다는 의미가 아니며 접근 가능한 적합한 차종의 실측 자료를 통한 보정은 후속 과제입니다.

## 시간·상황 기반 이상 주행 v6

화면·자동 생성 예제는 `combustion-events-6`를 기본으로 사용합니다. v1~v5는 저장 설정에 맞춰 이전 결과를 재생성하며, 버전 없는 API의 기본 v1도 유지합니다. v6는 v5의 도로·기어·RPM·부하·연료·온도 모델을 바탕으로 이상 주행의 발생 시점과 조건을 보완합니다.

`anomaly_vehicle_percent`는 후보 차량 선정 비율입니다. 차량 수×비율을 반올림하여 seed로 선정하며 대상 차량에서만 이상 이벤트를 허용합니다. 선정됐어도 실제 사건이 없을 수 있습니다.

`anomaly_events_per_hour`는 대상 차량 한 대의 운행1시간당 평균 **발생 기회**입니다(0~60). 절대 운행 시간에서 지수분포 대기시간의 포아송 후보 시계를 사용합니다. 예를 들어12는 평균5분마다 기회가 있다는 의미이며, 일정 간격/정확한 횟수/최소 발생량을 보장하지 않습니다. 메시지 주기를 바꿔도 후보 시각과 사건 계획은 바뀌지 않습니다. 시동 유지 정차도 운행 시간에 포함하지만 정차 중 사건은 발생시키지 않습니다.

후보는 현재의 정속 구간에서 검토하고, 웜업·가감속·정차 중 지나간 후보는 폐기합니다. 상황이 부적합하거나 직전 실제 사건 종료 후30초 이내이면 건너뜁니다. 미발생 기회를 적립하거나 이후 한꺼번에 실행하지 않습니다.30초는 개발용 회복 간격이며 국내 실차 통계값이 아닙니다.

| 종류 | v6에서 허용하는 상황 |
|---|---|
| 급가속 | 도심/간선/고속 도로, 회전 중이 아니고 교통 흐름 계수0.65 이상, 현재0.5m/s 이상 및 제어 상한까지4m/s 이상 여유 |
| 급감속 | 현재8m/s 이상, 혼잡/앞차 속도 조절 또는 정차 가능 도로 상황. 실제 앞차를 시뮬레이션한 충돌 회피 판단은 아님 |
| 급회전 | 기존 합성 경로에서 회전 후보가 있는 도심/간선, 현재5m/s 이상. 사건을 만들기 위해 고속 본선·진출입로·골목·보호구역에 급회전을 새로 강제하지 않음 |

`anomaly_intensity`는 v6에서만 `low`/`medium`/`high`를 지원하며 기본 `medium`입니다. 선택한 수준 안에서도 작은 seed 편차를 줍니다. 개발용 기본 가속도는 약3.05/3.325/3.6m/s², 감속도3.2/3.8/4.4m/s², 회전 횡가속도3.05/3.425/3.8m/s²입니다. 강우는 이 강도를90%로 완화합니다. 도로 제어 상한·진입 전 감속·차량 출력 제한은 유지합니다. 강도를 높여도 상황과 상한을 무시하거나 발생 횟수를 보장하지 않습니다.

최종 생성 구간에서 가속도≥3/감속도≤-3/횡가속도≥3m/s²와0.5초 이상 지속 조건을 확인하여 내부 이벤트로 표시합니다. 강우·출력·속도 여유 때문에 문턱에 못 미치면 사건으로 표시하지 않습니다. 특히 낮은 강도의 강우에서는 이벤트가 없을 수 있습니다. 이 문턱은 연속 선형 구간의 개발용 지표이며 법정 위험운전/TS 차종별 판정과 동일하지 않습니다.

상황표·그래프·선택 구간 Microtrip은 같은 모델로 재생성합니다. 이벤트/강도/발생 후보는 MQTT의 `em`/`xyz`나 새 OBD 필드로 추가하지 않습니다. 전량 시계열 DB 저장도 추가하지 않습니다. 현재는 가상 도로·앞차 상황이며 실제 지도/공유 교통/급작스러운 장애물·사고 대응을 검증한 모형이 아닙니다.

## 로컬 MQTT 성능·장애 측정

`python scripts/measure_mqtt.py --config configs/measurement.example.json`으로 반복 가능한 비교를 실행합니다. Go와 Python, 기존 Worker 의존성이 필요하며 새 Python 패키지는 필요하지 않습니다. 스크립트는 측정 전용 Worker와 시험 브로커를 빌드하고, 조건마다 별도 Worker 프로세스와 루프백 mTLS 브로커를 시작·종료합니다. 브라우저/API의 실행 DB를 사용하지 않습니다.

예제는10대(풀2/전체10),100대(풀10/전체100)의20초·2초 주기 비교와 연결1회 해제·PUBACK20ms 지연·응답없음·응답대기 중단을 포함합니다.10초 운행은1초 주기를 사용합니다. 시작/종료 Microtrip과 Trip을 포함하여10대120건,100대1200건입니다. 동일 비교 쌍은 차량·seed·주기·운행시간·연결유지 설정을 같게 둡니다. 주행 v6 모델·고정 Client 배정·QoS1/응답 미확인 시 자동 재발행 금지 정책을 유지합니다.

설정 파일의 `cases`에서 아래 항목을 조절합니다.

| 설정 | 의미·상한 |
|---|---|
| name | 조건 이름,1~60자 |
| vehicles / clients | 차량/Client 각각1~100. 풀은Client≤차량, 전체는같은 수 |
| mode | shared 또는 dedicated |
| duration_seconds / interval_ms | 운행10~60초/주기100~6000ms. 주기가 운행을 나누고10구간 이상 |
| lifetime | always(기본) 또는 while_driving |
| fault | none(기본), disconnect_once, delay_ack(20ms), no_ack, stop_wait |
| repeats | 전체 조건 반복1~3회. 조건1~12개·조건당5000건 이내·기본 예상 총15분 이내 |

측정 결과는 `.local/measurements/<시각-식별자>/summary.json`과 `summary.md`에 저장합니다. 요약 설정·상태·건수·성능 집계·CPU/RSS·브로커 수신/고유ID 개수만 남깁니다. 전체 OBD 메시지·인증서·개인 키·접속 프로필은 결과에 보관하지 않습니다. 일회성 키와 프로필은 시험 종료 시 정리합니다. 결과 디렉터리는 GitHub에 올리지 않으며 필요 없으면 해당 측정 폴더 단위로 삭제할 수 있습니다. 중간 결과도 조건 완료마다 기록합니다.

일반 MQTT의 소량 송신 상한은 유지합니다. 기존 단일 운행 측정 도구는100Client/5000건/120초/초당100접속·2000발행 설정을 유지합니다. 코어의 루프백 전용 확장 한도는 아래 일정 확장 계측에서1000Client/10000건/120초/초당200접속·5000발행까지 허용하며, `127.0.0.1` 또는 `::1`의 IP 주소만 허용합니다. localhost 같은 DNS 이름이나 외부 주소·AWS endpoint는 이 모드에서 거절합니다. 측정 스크립트는 외부 broker_url 입력을 받지 않고 자기 시험 브로커만 사용합니다. 현재 제어 API의 일반 MQTT 프로필에는 이 확장 설정을 노출하지 않습니다.

### 성능 결과 읽기

실제 MQTT 실행 결과에 `performance` 요약을 추가합니다. 이전 기록이나 송신 없는 생성 확인에는 없을 수 있습니다. 화면의 전송 성능 표는 아래 횟수/평균/최대/P95 상한을 표시합니다.

- 생성·검사: 메시지 생성·로컬 기록 집계/검사·직렬화 시간. 최초 차량별 계획 계산도 해당 메시지 생성 비용에 포함합니다.
- 예정 시각 대비 지연: 일시중지를 제외한 예정 시각부터 발행 직전 생성/직렬화 완료까지의 지연. 같은 시각에 차량 메시지가 몰리면 차량 순서에 따라 증가할 수 있습니다. always의 최초 연결 준비 이후에 전송 시계를 시작하므로 최초 접속 전체 시간은 이 값과 구분합니다.
- 접속 응답 대기: 각 Connect 요청부터 완료·실패·시간초과까지. 접속 속도 제한 대기/재시도 간격 자체는 제외합니다.
- 발행·PUBACK 대기: 각 Publish 요청부터 완료·실패·시간초과·중단까지. 성공/실패를 섞은 시도 시간이며 PUBACK 성공 건수는 기존 별도 카운터를 봅니다. 후속 파이프라인 처리 시간은 아닙니다.
- P95 상한: 1µs부터2배 간격의 고정 버킷으로 얻은95백분위 상한입니다. 예컨대32.768ms는 그 버킷의 상한이며 정확한 측정 P95값이 아닙니다. 횟수0이면0을 표시합니다. 전체 메시지별 지연열은 저장하지 않습니다.
- 평균 응답 처리량: PUBACK 성공 건수/연결 시작부터 정리까지 전체 경과시간. 주기 대기와 일시중지 시간을 포함하며 최대 발행 성능이나 Microtrip만의 초당 처리량이 아닙니다.

CPU·메모리는 별도 측정 보고서에 표시합니다. Windows는 GetProcessTimes의 사용자+커널 시간과 프로세스 working set을 사용하며, Linux는 /proc의 프로세스 CPU/RSS를 사용합니다. CPU100%는 코어1개 기준으로 장비 전체 사용률과 다르고, 브로커·제어 API·빌드 사용량은 제외합니다. RSS는250ms 관측 최댓값이므로 순간 최대/컨테이너 전체 메모리가 아닙니다. Linux는 마지막 표본 이후 종료까지의 CPU가 누락될 수 있고 자원 조회 불가 환경은 측정 불가로 표시합니다. 종료 관측 지연은 최대 약250ms이며 짧은 실행의 평균값에 영향을 줄 수 있습니다.

현재 Worker는 Client가 여러 개여도 메시지 발행과 PUBACK을 전역 순차 처리합니다. 전체 연결을 늘려도 발행 동시성이 늘지 않습니다. 일회성 시험 브로커는 CONNACK/PUBACK/PING의 최소 동작만 제공하며 운영 브로커의 저장·구독·혼잡 처리를 재현하지 않습니다. 짧은 단일 회차 결과로 연결 방식의 우열, 장시간 안정성, AWS 처리 용량/비용을 확정하지 않습니다. 반복·장시간·실제 운영 네트워크 측정은 별도입니다.

## Client별 동시 전송

연결 배정과 전송 처리 방식은 별개입니다. config.publish_mode는 serial(기본) 또는 parallel입니다. 기존 기록·미지정 요청은 순차 방식입니다. 화면에서 전송 처리 방식을 선택하고 실행 전에 고정합니다. 풀/전체 연결 모두 적용하며 실행 중 Client 증감·재배정은 없습니다.

parallel의 max_in_flight는 동시에 응답을 기다리는 Client 수 상한(1~100, 배정 Client 수 이하)입니다. 같은 Client에는 한 건씩 발행해 PUBACK 이후 다음 메시지를 보냅니다. 서로 다른 Client의 발행은 겹칠 수 있지만 전체 publish_per_second·connect_per_second 상한을 유지합니다. 접속/재접속 자체는 순차 처리이므로 느린 접속은 다른 작업의 응답 집계를 잠시 지연시킬 수 있습니다.

queue_capacity는 생성 후 발행 대기 중인 메시지의 실행 전체 상한(1~1000, 기본100)입니다. 진행 중인 응답은 이 상한과 별도입니다. 대기열이 가득 차면 새 생성을 늦추고 원래 예정 시각을 유지해 지연으로 집계합니다. 누락분을 조용히 버리거나 대기열을 무제한 늘리지 않습니다. 생성 순서·Client별 FIFO를 유지하고 발행 가능한 Client를 순환 선택합니다. 차량 간 도착 순서는 순차 방식과 달라질 수 있습니다.

일시중지는 새 생성/발행을 멈춘 뒤 진행 중인 응답을 기존 제한시간까지 집계하고 정지 완료를 알립니다. 이미 생성된 대기는 보존하며 재개 후 이어갑니다. 중단/실패 시 시작한 요청은 ACK 또는 미확인으로 정리하고 아직 발행하지 않은 대기 메시지는 폐기 수량으로 남깁니다. 응답 미확인은 자동 재발행하지 않으며 연결 정리 후 종료합니다. 한 Client의 응답 실패는 실행 전체를 실패 종료하는 정책입니다.

실제 MQTT 결과의 transmission에는 mode/max_in_flight/queue_capacity, 현재 및 최대 대기/진행 수, backpressure_count(대기열 포화 진입 횟수), discarded_queued(종료 시 폐기 대기 수)를 표시합니다. 대기열 수는 생성 완료했지만 발행을 시작하지 않은 메시지이고, 미생성/응답 미확인과 구분합니다. 순차 방식은 진행 수1이며 대기열을 사용하지 않습니다. 송신 없는 생성 확인은 MQTT 동시성을 시험하지 않습니다.

비교 실행: `python scripts/measure_mqtt.py --config configs/concurrency-measurement.example.json`. 동일 차량/주기/seed에서 순차와 동시를 비교하며 설정 파일에 publish_mode/max_in_flight/queue_capacity를 지정할 수 있습니다. 실제 주행 시각 분산은 추가하지 않았습니다. 짧은 루프백 결과로 AWS 최대 처리량이나 장시간 안정성을 확정하지 않습니다.

측정 주의: 이번 단일 로컬 비교에서 응답20ms 조건의 지연은 순차412ms→동시5개68ms로 감소했지만, 빠른 ACK의100대 조건은 동시 방식이 더 느렸습니다. 타이머·관리 비용과 장비 부하 영향이 있으므로 동시 전송을 항상 더 빠른 방식으로 간주하지 않습니다. 순차 기본값을 유지하고 실제 대상 조건에서 반복 비교하세요.

관리 모드의 화면용 진행 결과는 상태·일시중지 전환 시 즉시, 같은 상태에서는250ms 간격으로 갱신합니다. 내부 생성·ACK·오류 집계와 최종 결과의 정확도는 유지합니다. 메시지마다 전체 결과 JSON을 반복 출력하지 않으므로 화면에 모든 중간 카운터가 하나씩 표시되지는 않습니다. 최종 완료/중단/실패 결과는 별도로 출력·저장합니다. 즉시 처리 가능한 동시 전송 작업에는0초 타이머를 만들지 않습니다.

관리 진행 출력과 즉시 작업 대기 개선 후 단독 반복 측정(조건별2회)에서는100대풀 동시10의 최대 지연이497~504ms에서176~177ms로 감소했습니다. 순차는259~265ms에서219~225ms였습니다. 이는 짧은 루프백 표본이며 모든 연결/네트워크 조건의 우열이나AWS처리량을 보장하지 않습니다. 순차 기본값을 유지하고 실제 대상 조건으로 비교합니다.

## 차량별 일정 미리보기 (계획 전용)

`POST /api/schedules/preview`는 OBD 생성·MQTT 발행·실행 DB 저장 없이 차량별 운행 계획과 예상 메시지 수를 반환합니다. 웹은 이 API로 일정을 구성하고, 저장된 일정은 전체 실행 API에서 사용합니다. 기존 v1~v6 생성 결과는 바꾸지 않습니다. 입력 예제는 configs/schedule-manual.example.json, configs/schedule-patterned.example.json입니다. 예제는 개발용 설정이며 국내 실측 비율이 아닙니다.

PowerShell 호출 예:

```powershell
$body = Get-Content -LiteralPath configs/schedule-manual.example.json -Raw -Encoding utf8
Invoke-RestMethod -Method Post -Uri 'http://127.0.0.1:8080/api/schedules/preview?offset=0&limit=100' -ContentType 'application/json; charset=utf-8' -Body ([Text.Encoding]::UTF8.GetBytes($body))
```

measurement.start/end는 UTC offset 포함 ISO8601(최대 밀리초), timezone은 초기 Asia/Seoul입니다. 시작·종료 시각 모두 메시지 관측에 포함합니다. 실제 운행 start/end는 양수 기간이며 종료 전까지만 출발 기준 interval_ms 주기의 Microtrip을 계산하고 종료 시각에는 Trip 한 건만 계산합니다. 종료가 주기 격자와 맞아도 종료 Microtrip을 추가하지 않습니다. 측정 시작 전 출발은 원래 주기 위상을 유지하고 전체 운행 시작/종료를 결과에 보존합니다. 측정 종료 이후 도착이면 정상 Trip 수는0입니다. 아직 실제 메시지 내용이나 시험용 강제 종료 Trip을 생성하는 기능은 아닙니다.

manual은 차량별 trips 목록을 받으며 빈 목록은 미운행입니다. 같은 차량의 모든 입력 운행은30분 이상 주차 간격이 필요합니다. 중첩·30분 미달은 오류이며 자동 병합/수정하지 않습니다. 자정 통과 운행은 하나로 유지합니다. 직접 지정 시간은 시험 일정이며 실제 경로/교통에 따라 도착을 계산한 값이 아닙니다.

patterned는 차량별 pattern을 받습니다. weekdays는 월1~일7, day_off_probability는 해당 요일 미운행 확률, baseline_jitter_minutes는 차량별 고정 출발 편차입니다. slots에 HH:MM 출발·최소/최대 운행분·날짜별 출발 편차·road_profile을 지정합니다. 날짜별 overrides(YYYY-MM-DD:운행 목록)가 요일/미운행 추첨보다 우선하고 빈 목록은 그날 미운행입니다. 예외 운행의 한국 날짜상 출발일이 키 날짜와 일치해야 합니다. 운행은 다음 날까지 이어질 수 있습니다. 자동 편차 때문에30분 간격이 깨지면 무한 재추첨하거나 몰래 생략하지 않고 오류를 반환하므로 슬롯/편차/예외를 조정하세요. 자동 목적지·귀환 경로/실제 교통은 후속입니다.

seed·일정 버전·차량ID·한국 날짜·슬롯에 따른 일정은 같은 설정에서 재현됩니다. 실행 ID·조회 페이지 순서는 난수에 사용하지 않습니다. trip_key/tid는 차량·운행 시각·도로 프로필·버전에서 결정하며 관측 범위/페이지 변경만으로 바뀌지 않습니다. tid는 아직 실제 수신 시스템의 호환성 확정 번호가 아닙니다.

결과는 관측 운행 목록(trips), 차량별 운행/주차 시간 합계(vehicles), 미운행 차량ID, 예상 Microtrip/Trip 수와 페이지 정보를 제공합니다. 전체 운행 목록이 아니라 최대100건 페이지이며 집계는 전체 관측 범위 기준입니다. 주차시간은 시동 OFF 계획 구간의 길이이며 신호 대기시간 분석이 아닙니다. 이 계획 응답 자체에는 OBD 위치/거리/연료가 없으며 별도 조회·실행에서 같은 일정의 OBD를 생성합니다.

초기 계획 전용 상한은 차량100대·측정30일·입력/생성 전체운행10,000회·단일운행24시간·자동 하루16슬롯입니다. 생성된 문맥 운행(관측창 앞뒤 날짜 포함)도 계획 상한에 포함합니다. 앞뒤 날짜 문맥의 주차 충돌도 오류가 될 수 있습니다. 차량1만대 지원이나30일 센서 전량 생성/전송을 의미하지 않으며 기존 생성·MQTT 상한은 유지합니다. 직접 입력과 자동 pattern은 혼용하지 않습니다. API의 현재 제한과 맞지 않는 입력은422로 안내합니다.

일정 날짜 예외는 해당 기준 날짜의 출발 슬롯을 대체합니다. 빈 목록이더라도 전날부터 이어지는 운행을 강제로 자르지 않습니다. 출발 편차로 날짜 경계를 넘는 슬롯도 있을 수 있으므로 완전히 운행이 없어야 하는 날짜는 인접 날짜의 슬롯/명시 일정까지 함께 확인하세요. 이는 초기 일정 계획기의 제약이며 실제 휴무일 운행을 검증한 통계 모델이 아닙니다.

## 일정 기반 OBD 로컬 조회

`POST /api/schedules/obd/{vehicle_id}/{trip_key}`에 `{"schedule": <일정 요청 객체>}`를 보내면 선택 운행의 OBD 형식 합성 데이터를 로컬 생성합니다. trip_key는 일정 미리보기 결과에서 가져옵니다. 선택 차량의 선행 운행부터 상태를 복원하므로 다음 운행은 이전 도착 위치·차량 총주행거리·방향·주차 후 냉각수 온도에서 시작합니다. 차량 사양과 운전자 성향은 차량 seed로 고정하고 각 운행의 움직임은 운행별 seed로 구분합니다. 운행 연료·운행거리는 Trip마다 새로 누적합니다.

선택 입력은 initial_lat/lon, initial_odometer_m, initial_coolant_c, force_end_trip(기본false)입니다. 첫 계획 운행의 초기 상태이며 조회 구간 시작마다 초기화하지 않습니다. 외기20℃/냉각 시정수2시간은 실차 보정 전 개발 가정입니다. 배터리는 기존 차량별 시동/충전 근사를 사용하며 주차 중 전장 부하·배터리 잔량까지 연속 모델링하지 않습니다.

쿼리는 start_ms/end_ms(UTC ms, 관측 범위 안에서 추가 제한), offset(0~1,000,000), limit(1~100)입니다. 결과 messages는 해당 구간의 Microtrip만 최대100건, trace는 최대120점, trip은 운행 전체 요약 또는없음입니다. 실제 종료에는 Trip만 생성하고 종료 Microtrip은 만들지 않습니다. 기간 경계에 새 시동을 만들지 않으며, 주차 구간에는 메시지를 만들지 않습니다. trip은 실제 종료가 조회/관측 범위에 있을 때만 반환합니다. 조회만으로 MQTT 발행·전체 메시지 저장은 하지 않습니다. 차량 종료 상태는 별도 로컬 캐시에 제한해 보관합니다. 웹의 ‘차량 데이터’ 탭에서 차량 일정·시간선·구간 조회를 사용할 수 있습니다.

force_end_trip=true는 측정 끝에 운행 중인 경우 잘린 시험용 Trip을 로컬로 반환합니다. synthetic_trip=true와trip_scope로 표시하며 pld에 미확정 식별 필드를 추가하지 않습니다. 해당 시각까지의 거리/연료/시간만 집계하고 마지막 시각의 Microtrip 대신 시험 Trip을 반환합니다. 이미 실제 종료했다면 정상 Trip만 반환하여 중복하지 않습니다. 조회의 중간 종료 시각을 임의의 강제 종료 시각으로 쓰지는 않습니다. 시험용 Trip의 전송 토픽/식별 계약이 아직 없으므로 이 기능에서 MQTT로 발행하지 않습니다. 조회 결과는 실제 종료 이력을 변경하지 않습니다.

운행 길이는 정수 초만 지원합니다. 후반 운행은 중간 상태에서 이어 계산하며, 미준비 구간은 요청당 최대16회·48시간씩 나누어 준비합니다. 일정 계획 자체의30일/최대24시간 운행 지원과 생성 조회의 상태 복원 상한은 별개입니다. 한 Worker 호출15초·한 조회 복원30초의 제한이 있습니다. 자동 일정의 시작 상태는 관측 기간 앞뒤 문맥의 첫 계획 운행을 기준으로 하므로 같은 요청의 부분 조회/페이지는 재현되지만 측정 기간 자체를 바꾸면 과거 문맥과 상태가 달라질 수 있습니다. 장기 조회의 로컬 중간 상태는 아래 관리 절을 참고하세요. 실제 지도·목적지 귀환·시간대 공유교통·실제 자동 도착 계산은 후속입니다. 기존 v1~v6 실행/저장 결과를 새 규칙으로 재해석하지 않습니다.


## 통합 작업공간 사용하기

왼쪽 작업 기록에서 기존 실행과 새 일정을 함께 찾고, 중앙의 **조건 설정 → 차량 데이터 → 연결·전송 → 저장소** 탭으로 이동합니다. VS Code의 탐색기·작업 패널과 Grafana의 데이터 탐색 방식을 참고한 자체 React 화면이며 별도 제품 설치는 필요하지 않습니다.

1. **새 시뮬레이션**에서 작업 이름과 전체 차량 조건을 입력하고 **일정 생성·기록**을 누릅니다. 개별 차량 설정은 점검용으로 유지합니다. 설정과 예상 건수·차량 요약만 실행 DB의 workspace_plans에 저장하며 전체 메시지는 추가 저장하지 않습니다. 저장하지 않은 입력은 새로고침 후 복원되지 않습니다.
2. **차량 데이터**에서 차량과 운행을 선택하고 **선택 운행 OBD 생성·조회**로 그래프·Trip·Microtrip을 확인합니다. 그래프 드래그 또는 KST 시작/종료 입력으로 구간을 조회하며 Microtrip은100건씩 탐색합니다. 표의 행을 선택하면 한국어 항목명과 원래 필드의 전체 값을 확인하고 JSON 버튼으로 OBD 본문만 볼 수 있습니다. Trip 요약은 해당 운행 전체 기준입니다.
3. 저장된 일정은 설정을 고정합니다. **설정 복사**로 새 작업을 편집하며 원본을 덮어쓰지 않습니다. 기록을 다시 열면 저장 조건으로 차량 목록을 재구성하고 OBD는 요청 시 재생성합니다. 생성 코드가 바뀌면 재생성 결과가 바뀔 수 있으며 과거 전송 원문 보관 기능이 아닙니다.
4. **연결·전송**에서는 현재 일정의 생성 확인 또는 실제 MQTT 실행을 선택합니다. **고급 · 소량 연결·전송 시험**에는 기존 수동 입력·단일 운행 생성과 연결 풀/차량별 연결 시험을 유지합니다. 이 시험의 입력은 현재 일정과 별개이며, 시작한 실행은 같은 작업 기록에 표시됩니다. 실제 발행/PUBACK·진행 상태·일시정지/재개/중단과 차량별 구간 조회는 실행 기록에서 확인합니다. 기존 실행의 설정과 생성 모델은 자동 변환하지 않습니다.
5. 왼쪽은 최근50개 작업의 검색·일정/실행 필터·선택 삭제를 지원합니다. 삭제 전 대상 목록을 확인하며 실행 중·일시정지된 기록은 보호됩니다. 기록 삭제와 **저장소**의 중간 상태 비우기는 별도 동작입니다. 사용자 기록은 자동으로 지우지 않습니다.
6. 탐색기를 접거나 너비를 조절할 수 있고 **집중 보기**는 Esc로 해제합니다. 밝은/어두운 테마 선택은 현재 브라우저에 보관합니다. **Ctrl+K**는 빠른 명령, 하단 **작업 활동**은 현재 화면에서 수행한 작업, **선택 기록의 설정**은 저장 요청을 보여줍니다. 작업 활동은 브라우저 메모리에 최대100개이며 서버 원문 로그가 아닙니다.

미운행 차량은 관측 운행0회로 표시하고 이전 OBD 결과를 비웁니다. 차량/운행 전환 시 진행 요청의 이전 응답을 차단합니다. 생성 중 입력 잠금과 중간 상태 분할 준비·진행률·준비 중단은 기존 정책을 유지합니다. 조회 시각은 UTC 밀리초를 보존하고 화면에는 KST를 사용합니다. 저장 조건의 날짜 예외는 고급 JSON에서 입력하며 적용 전 서버 검증을 거칩니다.

## 전체 조건으로 차량 일정을 자동 배정하기

새 웹 기본값은 fleet-plan-2의 다양한 생활 운행입니다. 아래의 하루 목표 합계/횟수 균등 배분 설명은 이전 fleet-plan-1에 해당하며, 새 배정은 하단 ‘다양한 생활 운행과 시간·속도·거리’ 절을 참고하세요. 기존 기록의 설정은 자동 변경하지 않습니다.

‘조건 설정’의 기본 설정 범위는 **전체 조건 자동 배정**입니다. 차량 수·측정 기간·주기·운행 성격·운행일 하루 목표 시간·차량 간/날짜별 편차·하루 미운행 확률·이상 이벤트 대상 비율/빈도/강도를 입력하면 시스템이 차량 명부와 세부 운행을 생성합니다. 명부나 차량별 운행 JSON을 직접 작성할 필요가 없습니다. 기존 차량별 폼은 ‘개별 차량 설정 · 점검용’으로 전환해 사용할 수 있습니다. 설정 범위 전환 시 조회 결과를 비우고 각 폼의 입력은 유지합니다.

새 기본 배정 예제는 configs/fleet-diverse.example.json(fleet-plan-2)이고, configs/fleet.example.json은 이전 fleet-plan-1 재현용입니다. API는 `POST /api/fleets/preview`에 이 객체 하나를 보내며, 차량 수와 무관하게 요청에 vehicles 배열을 넣지 않습니다. 차량·운행 목록은 기존과 같이 offset/limit/vehicle_id로 조회합니다. 표본 OBD는 `POST /api/fleets/obd/{vehicle_id}/{trip_key}`에 `{"fleet": <전체 조건 객체>, "force_end_trip": false}`를 보내며 start_ms/end_ms/offset/limit 쿼리를 지원합니다. 미리보기와 OBD 조회는 같은 전체 조건을 사용해야 합니다. 미리보기 API 자체는 설정·모델/버전·seed로 재생성하며 저장하거나 MQTT로 전송하지 않습니다. 웹의 ‘일정 생성·기록’은 별도 API로 설정·요약만 저장합니다.

- **운행일 하루 목표 시간**은 운행하는 날짜의 총 운행 시간 목표입니다. 차량별 고정 목표 차이에 날짜별 편차를 곱하고 정수 분으로 반올림합니다. 미운행일·측정 경계·표본 차이 때문에 전체 관측 평균과 일치하지 않을 수 있습니다. 두 편차의 최대 조합은 하루600분 이하로 제한하고 초과하면 목표/편차 조정을 안내합니다.
- **차량별 생활패턴**은 명부에서 고정 배정합니다. 혼합 예시60/20/20, 출퇴근 중심80/10/10, 비정기 중심20/30/50은 개발 예시입니다. 차량 수×비율의 정수 부분을 먼저 배정하고 남은 차량은 소수 부분이 큰 패턴부터 배정합니다. 동률은 패턴 키 순으로 처리합니다. 이는 한국 운전자 실측 구성비가 아닙니다.
- **날짜별 운행**은 출퇴근형2회, 주간형2~3회, 비정기형1~3회로 배치하는 초기 개발 모델입니다. 차량별 기본 출발 시각에 날짜 편차를 적용하고 최소30분 주차와 자정까지의 여유를 고려해 후속 운행을 배치합니다. 운행 길이를 과속으로 맞추거나 출퇴근 시각에 맞춰 순간 이동시키지 않습니다. 날짜별 총 시간과 개별 출발/종료는 시스템이 정합니다. 주말에는 비정기 시간 배치를 사용합니다.
- **하루 미운행 확률**은 기간 전체 미운행 차량 비율과 다릅니다. 주말은 별도 참여 확률로 후보일을 정한 뒤 하루 미운행 확률도 적용합니다. 예를 들어 주말 참여50%·미운행20%이면 주말 운행 가능성은40%입니다. 실제 유한 표본의 비율은 이 값과 다를 수 있습니다.
- **이상 이벤트 대상 비율**은 전체 차량 수×비율을 가장 가까운 정수(0.5 올림)로 반올림한 수의 고정 대상입니다. 조회/페이지/날짜에 따라 대상이 바뀌지 않으며 미운행 대상 차량도 있을 수 있습니다. 후보 빈도는 대상 차량의 운행1시간당 기댓값이고 실제 사건 수 보장이 아닙니다. 기존 event-6 생성기의 도로·속도·회복 조건을 통과한 사건만 적용합니다. 비대상 차량에는 의도적인 이상 사건을 주입하지 않습니다.
- **도로 배정 비중**은 차량의 도로 성격을 고정 추첨하는 가중치입니다. 실제 차량 수 비율과 정확히 일치하도록 강제하지 않습니다. 운행 안의 도로 관계는 기존 경로 생성 모델을 사용합니다. 실제 도로 지도·목적지 귀환·공유 시간대 교통을 수입한 기능은 아닙니다.

화면은 전체 예상 메시지/운행 수와 이상 대상 차량 수를 표시하고, 선택 차량의 패턴·대상 여부를 보여줍니다. 차량별 그래프·Trip·Microtrip의 표/JSON·구간 조회는 기존 기능을 그대로 사용합니다. 배정 정보와 도로 상황은 로컬 설명정보이며 OBD 본문에는 추가하지 않습니다. OBD 응답의 events_until_query_end는 실제 운행 시작부터 조회 종료까지 내부 모델이 집계한 사건 수입니다. 조회 시작 전 구간도 포함하며 최대120점 그래프에서 센 사건 수가 아닙니다. 개발 확인용 집계이며 전송 필드가 아닙니다.

현재 계획 제한은100대·최대30일·앞뒤 문맥 포함10,000운행입니다. OBD 선행 복원은16회/48시간을 요청 한 회차의 한도로 사용하고 중간 상태를 이어 후반 운행까지 준비합니다. 차량 수 입력을 간소화한 것이1만대/30일 OBD 생성·전송 지원 완료를 뜻하지 않습니다. 앞뒤 날짜는 기존 모델처럼 과거 상태 복원을 위한 문맥이며 관측 기간을 바꾸면 초기 상태 기준도 달라질 수 있습니다. 생활패턴·요일별 일정은 같은 날짜/설정/seed에서 재현되지만 과거 물리 상태는 해당 설정과 관측 기간의 초기 문맥을 기준으로 제한된 중간 상태 캐시에 보관합니다. 관측 기간 자체를 바꿔도 같은 절대 상태를 보장하는 장기 이력 저장소는 아닙니다. 모든 차량의 최초 위치/거리 기준은 기존 로컬 기본값이며 전국 차량의 초기 위치/누적거리를 실측 분포로 배정한 모델은 아닙니다.


## 장기 운행 조회와 중간 상태 관리

‘차량 데이터’ 조회는 선택 차량의 운행 종료 상태를 .local/obd-state.sqlite3에 보관합니다. 실행 기록 DB(.local/runs.sqlite3)와 분리되어 있으며 전체 Microtrip·Trip 본문·그래프·인증 정보를 저장하지 않습니다. 보관 항목은 생성 조건을 구분하는 해시, 운행 순번/실제 모델 종료 시각, 위치·총주행거리·냉각수 온도·방향 및 마지막 사용 시각입니다. 시험용 종료 Trip을 선택해도 캐시에는 원래 운행의 실제 모델 종료 상태를 저장하므로 잘린 시험 요약으로 후속 상태를 바꾸지 않습니다.

- 전체 저장소의 기본 보관량은 최대2,048개 종료 상태, 마지막 사용 후24시간입니다. 만료 항목은 다음 저장소 접근 때 정리하며, 한도에 도달하면 가장 오래 사용하지 않은 항목부터 제거합니다. 새로 만드는 DB는4KiB페이지·최대1024페이지로4MiB를 제한하고 자동 페이지 반환을 사용합니다. SQLite의 일시적인 트랜잭션 journal은 이 DB 본문 상한과 별개입니다.
- 설정·seed·관측 기간·초기 상태·이상 이벤트 설정·생성 정책 코드·Worker 바이너리 내용이 다르면 이전 상태를 재사용하지 않습니다. 이전 조건의 항목은 즉시 전량 삭제하지 않고 만료/보관량 정책으로 정리합니다. 부분 조회 구간·메시지 페이지·시험용 종료 여부는 실제 차량 종료 상태의 식별을 바꾸지 않습니다.
- 가장 가까운 이전 종료 상태를 찾고 남은 운행만 계산합니다. 처음 보는 후반 구간은 요청 한 회차당 최대16회/누적48시간·복원30초·Worker호출15초의 기존 자원 한도로 나누어 준비합니다. 화면이 후속 요청을 보내며 진행률을 표시합니다. 화면 자동 준비는 최대100회 요청이며, 도달하면 완료된 상태를 유지하고 재조회를 안내합니다. 한 Worker 자체가 시간 제한을 넘는 경우 오류를 표시하고 이미 완료한 상태는 남습니다.
- ‘이후 준비 중단’은 추가 요청을 중단합니다. 이미 서버에 전달한 한 회차는 끝날 수 있으며 완료된 상태는 재사용합니다. ‘차량 중간 상태 관리’에서 보관량/DB 크기를 새로고침하거나 ‘중간 상태만 비우기’를 사용할 수 있습니다. 비우기는 화면의 자동 준비를 함께 중단하고 저장소 세대를 바꿔 이전 세대의 쓰기를 차단합니다. 설정·실행 기록·이미 표시한 결과는 유지하고 다음 조회에서 상태를 다시 생성합니다.
- 서버 재시작 후에도 유효한 중간 상태를 재사용합니다. 다른 화면에서 저장소를 비운 경우에도 새 조회는 최신 세대를 확인합니다. 동시 조회의 DB 쓰기는 트랜잭션으로 보호하지만 동일 차량 계산의 중복 수행을 분산 조정하는 기능은 아닙니다. 대량 동시 요청의 처리량을 보장하는 분산 캐시/작업 큐로 취급하지 않습니다.

관리 API는 `GET /api/checkpoints`(entries/max_entries/ttl_seconds/database_bytes/max_database_bytes/epoch)와 `DELETE /api/checkpoints`입니다. DELETE는 재생성 가능한 중간 상태만 비우고 갱신된 통계를 반환합니다. 장기 OBD API는 미완료이면 HTTP202/status=preparing과 restoration(완료한 선행 운행/전체 선행 운행/이번 계산 수/재사용 수/checkpoint_epoch)을 반환합니다. 같은 요청을 반복하면 HTTP200/status=generated_local_only와 기존 OBD 결과를 반환합니다. 최초 요청에 GET에서 읽은 epoch를 최상위 checkpoint_epoch로 보내고, 후속 요청에도202의checkpoint_epoch를 유지하면 중간에 비워진 경우 HTTP409로 중단됩니다. epoch를 생략한 요청은 당시 저장소에서 새로 시작하는 독립 요청입니다. 저장소 접근 실패는 HTTP503으로 안내합니다.

전체 조건 미리보기는 전역 건수를 계산하기 위해 전체 차량을 순회하지만, 날짜별 운행을 한 차량씩 생성해 집계합니다. 선택 차량 OBD 조회는 다른 차량의 날짜별 일정을 펼치지 않고 선택 운행이 나올 날짜까지만 구성합니다. 기존 차량 수/기간/전체 계획 수 상한과 한국 실차 보정·지도/공유교통 미구현 상태는 유지합니다. 일정 MQTT 전송에는 별도 서버 상한을 적용합니다.


## 전체 일정 생성 실행

저장된 일정을 선택하고 **연결·전송 → 현재 일정 전체 실행**에서 실제 시간 또는 가상시간을 선택한 뒤 **전체 일정 생성 실행 시작**을 누릅니다. 차량별 OBD 조회는 사전 필수 절차가 아닙니다. 차량마다 다른 출발·주차·재출발·종료를 자동 처리하며 운행 시작부터 종료 직전까지 Microtrip, 실제 종료 시 Trip을 생성합니다. 운행이 없는 차량도 고정 배정 명부에는 남습니다.

- 초기 실행 상한은 측정 기간1시간·전체10,000메시지입니다. 장기 계획/조회 상한과 다르며3일 기본 계획을 그대로 실행하면 조정을 안내합니다. 실제 시간은 설정한 과거/미래 날짜를 기다리는 예약 실행이 아니라 측정 시작을 실행 시점에 대응시켜 재생합니다. 주차 시간도 진행하며 측정 종료까지 실행합니다.
- 가상시간은 대기 없이 같은 메시지를 시각순으로 생성하는 로컬 확인입니다. MQTT 배속 전송이 아닙니다. 송신 없는 확인에서는 연결·발행·PUBACK는0이며 고정 배정표만 기록합니다. 실제 MQTT 송신은 아래 절의 서버 설정과 별도 상한을 적용합니다.
- 실행 기록에서 진행률·지연·건수·최대10건 샘플을 확인하고 일시정지/재개/중단합니다. 일시정지는 생성 메시지의 시간축을 멈추지만 전체 제한시간은 흐릅니다. 실제 시간의 전체 제한은 측정 기간+30초, 가상시간은120초입니다. 진행 중 생성 한 회차는 최대 기존15초 Worker 제한 안에서 끝날 수 있으며 중단은 이후 메시지를 처리하지 않습니다. 중단 자체로 종료 Trip을 만들지 않습니다.
- **측정 끝에 운행 중인 차량의 시험용 Trip 생성**은 전체 차량에 적용합니다. 경계까지의 Microtrip 대신 시험 요약을 만들며, 정상 종료와 중복하지 않습니다. 실행 샘플의 synthetic_trip은 로컬 표시정보이고 OBD 본문에 추가하지 않습니다. 시험 Trip 식별 전송 계약은 미확정이며 외부에 발행하지 않습니다.
- 저장 조건을 복사하여 실행 요청에 고정합니다. 전체 메시지 전량 저장 없이 차량별 최대100건 조회 페이지와 시간순 병합을 사용하고, 최종 기록은 집계·고정 배정·최대10건 샘플만 보관합니다. ‘원본 일정의 차량 데이터 조회’로 상세 구간을 재생성합니다. 실행 중 중간 상태를 비우면 이전 세대의 후속 생성은 실패로 중단합니다. 생성 준비 비용도 지연에 포함되므로 지연0의 실시간 보장이나 대규모 처리 완료를 뜻하지 않습니다.

## 일정용 주행 모델 v7

schedule-obd-2/traffic-7은 이전 일정 주행 모델입니다. 현재 일정 조회와 전체 실행은 아래 설명의 schedule-obd-3/journey-8을 함께 사용합니다. 기존 v1~v6 저장 실행의 재생성 규칙은 유지합니다. 일정 기록은 조건/요약이므로 기존 일정도 재조회하면 현행 일정 모델을 사용합니다.

도심 기본50km/h를 유지하고 지정 간선60km/h, 외곽의 제한표지 간선60/70/80km/h를 구분합니다. 간선 구간은 도로 프로필과 함께 정한 개발용 가상 경로이며 실제 지도·표지 데이터가 아닙니다. 차로 수만으로 고속을 부여하거나 모든 도심을 빠르게 만들지 않습니다. 고속 본선/진출입로/도심 접근 구조는 유지합니다.

목표 속도는 이전 선호 상태에서 점진적으로 변하고,3~12초 소구간에서도 완만하게 변속합니다. 정상 가감속·엔진 출력·곡선 횡가속 제약과 거리/연료 집계는 함께 적용합니다. 정차 확률을 짧은 구간마다 동일 적용하지 않고 시간 간격에 따라 계산하며 정차 후 최소 여유를 둡니다. 이 편차·확률·간격은 실차 통계에서 추정한 수치가 아닌 개발 가정입니다. 앞차는 교통 흐름의 근사이며 실제 다른 차량의 위치/차간거리 추종은 아닙니다.

주행 상태표와 출발 상태 설명의 냉각수 표시는 제거했습니다. 엔진·주차 연속성의 내부 냉각 계산과 기존 OBD Trip ctp 계약/원본 JSON은 유지합니다. 그래프는 기존 최대120점 요약이므로 미세 변화는 구간을 좁혀 확인합니다. 한국 주행의 대표성을 검증한 실차 보정 모델은 아닙니다.


## 전체 일정 MQTT 전송

서버의 .local/mqtt.json(또는 DANGUBI_MQTT_PROFILE)에 시험 브로커·CA·클라이언트 인증서/키 경로·토픽·권한 확인·상한을 먼저 설정합니다. 이 접속 프로필은 실행 요청/DB/화면에 복사하지 않습니다. 같은 TLS1.2 이상·CA/서버명/클라이언트 인증·MQTT3.1.1·QoS1·retain=false 정책을 기존 소량 전송과 일정 전송에서 사용합니다.

**일정 선택 → 연결·전송 → 일정 전송 방식: 실제 MQTT 송신 → 연결 풀/차량별 배정·Client 수·유지 정책 지정 → 실제 송신 확인 → 전체 일정 MQTT 실행 시작** 순서입니다. 차량별 조회 버튼은 필요하지 않습니다. 접속 설정이 준비되지 않으면 MQTT 선택을 비활성화합니다. 설정을 준비한 뒤 화면을 새로고침하세요. 프로필 준비 상태는 실제 접속 성공을 의미하지 않습니다.

- 실제 시간 전송만 지원합니다. 가상시간/시험용 Trip 옵션을 함께 요청하면 API가422로 거절합니다. 측정 끝에 아직 운행 중인 차량은 종료 전 Microtrip까지만 보내며 가짜 종료 Trip을 만들지 않습니다. 중단 시에도 새 종료 Trip을 만들지 않습니다.
- 서버의 일반 MQTT 상한은 그대로입니다. 기본 Client5개/메시지20건/전체30초, 코드 최대20개/100건/30초입니다. 측정 기간은 전체 제한보다 짧아야 하고 접속·발행·응답 여유가 필요합니다. 로컬 생성의1시간/10000건이나 성능측정 전용 확장 프로필을 일반 송신 상한으로 사용하지 않습니다.
- 기간 내내 유지는 모든 고정 Client를 시작할 때 접속하고 측정 끝에 해제합니다. 운행 중 유지는 같은 Client에 배정된 차량의 관측 운행 구간 합집합을 따릅니다. 한 대라도 운행 중이면 유지하고 모두 주차하면 마지막 메시지 응답 후 해제합니다. 같은 시각의 출발→발행→운행 종료 순서로 처리해 불필요한 끊김을 피합니다. 신호 대기·정체는 운행 중입니다. 측정 시작 전부터 운행 중인 차량도 관측 시작부터 연결합니다.
- Client 수/배정표는 실행 전 고정합니다. 주차 후 정상 재접속은 연결 성공 횟수(connection_count)에 포함하고 장애 재연결(reconnect_count)과 구분합니다. connected_clients는 한 번 이상 연결한 고유Client 수, active_clients는 마지막 확인 시점의 열린 연결 수입니다. 최종 연결 정리를 확인하지 못하면 완료로 확정하지 않습니다.
- 일정 전송은 Client별 병행 방식입니다. Client 하나는 최대 한 건의 PUBACK을 기다리며, 다른 Client는 병행 발행합니다. 전체 진행 명령 상한은 고정 Client 수이고 동일 Client의 연결·발행·해제는 한 순서를 공유합니다. 차량별 발행 호출 순서를 유지하지만 서로 다른 Client의 도착 순서는 보장하지 않습니다. 전체 publish_per_second/connect_per_second는 공유하므로 Client 수만큼 배수로 늘지 않습니다. 송신 Go 프로세스는 하나이며 내부에서 Client들을 병행 처리합니다.
- 공통 송신 예산은 대기·진행 중인 명령을 합쳐100건/1MiB입니다. 연결·해제 명령도 포함하며 바이트는 명령 본문의 UTF-8 JSON 크기 기준입니다. ID·예정시각 등 통신 부가 필드, 언어 객체·런타임·생성 페이지까지 포함한 전체 RAM 상한은 아닙니다. 가득 차면 새 메시지 인출을 기다리며 임의 폐기하지 않습니다. 일정 MQTT도 아래 생성 Worker 풀을 사용하며 페이지는 생성 예산에 맞춰1~100건으로 조절합니다. backpressure_count는 예산 부족으로 생산을 기다린 횟수입니다. 느린 ACK 자체의 횟수와 다릅니다.
- 연결 장애는 동일 Client ID로 제한 재시도합니다. Publish 응답이 불명확하면 수신됐을 가능성이 있으므로 자동 재발행하지 않고 전체 실행을 실패로 정리합니다. 이미 진행 중인 다른 Client도 응답/미확인을 집계하며 대기 발행은 취소합니다. QoS1의 중복 가능성을 제거하거나 후속 저장 완료를 보장하지 않습니다. 일시정지는 새 명령 시작을 멈추고 진행 명령을 모두 집계한 뒤 완료합니다. 대기열과 연결은 보존하며 재개 시 이어 보냅니다. 정지 시간에도 전체 MQTT 제한시간은 흐릅니다.
- DB에는 원본 일정 스냅샷·고정 배정·집계·최대10건 샘플만 보관합니다. 토픽은 topic_prefix/run_id/vehicle_id/obd이며 본문은 ty/ts/pld만 보냅니다. 화면 조회로 재생성한 값은 당시 브로커 수신 원문을 대체하지 않습니다. performance의 connect/ack/schedule은 접속·응답 대기·발행 호출 직전의 예정시각 대비 지연 집계이며 schedule_delay_ms는 그 최대 지연입니다. 일정 실행의 generation.count0은 생성 시간 분포 미집계를 뜻합니다. 최초 접속 준비도 일정 실행 시계에 포함됩니다.
- 일정 결과 transmission의 per_client_in_flight는1, max_in_flight는고정Client수입니다. in_flight는접속/속도제한/PUBACK대기를포함한진행중발행명령, queued_messages는발행전대기메시지, reserved_commands/reserved_bytes는연결명령·대기·진행합계입니다. peak_*는각최대, queue_capacity/queue_byte_capacity는예산입니다. 종료시대기메시지는discarded_queued/discarded_queued_bytes로집계하고예약량을0으로정리합니다. 이미시도한미확인발행은unconfirmed_messages이며대기취소와구분합니다. 이전기록의mode=serial과backpressure_count는이전순차방식의정의를보존합니다.

`python scripts/dev.py test`는 기존 시험과 services/control/test_schedule_mqtt.py를 함께 실행합니다. 일정 통합 시험은 일회성 루프백 mTLS 브로커·인증서·임시DB를 사용해 연결 방식/유지·겹친 운행/주차·본문 일치·PUBACK·장애 재연결·응답 없음·지연·일시정지/재개/중단을 확인하고 종료합니다. 실제 AWS나 사용자의 접속 프로필/기록은 사용하지 않습니다. AWS 접속은 endpoint·토픽·인증서·정책이 준비된 뒤 별도로 확인하며, 운영 배포 환경은 아직 선택하지 않았습니다.

- 새 웹 예시의 도로 가중치는 도심35/고속20/정체5/혼합40입니다. 목적별 길이 범위·비율·기준60분·도로 가중치는 한국 실차로 추정한 수치가 아닌 초기 개발 선택입니다. 목표 시간/편차 조합의 기존600분 상한과 계획100대/30일/10,000문맥 운행 및 실행·MQTT 상한은 유지합니다.
- 일정 주행 모델 journey-8은 정체 성격을 운행 전체에 강제하지 않습니다. 혼잡→부분 회복→원활 같은 수십초~수분 교통 에피소드에 한국 시간의 출퇴근 시간대와 도로 조건을 반영합니다. 도로 구간은 수분 단위로 이어지고 간선 커브는 완만한 반경을 사용할 수 있습니다. 개별 차량 생성의 시간대 근사이며 같은 장소의 여러 차량이 서로 영향을 주는 공유 교통망은 아닙니다.
- 거리값은 속도와 운행 시간을 적분한 결과입니다. ‘1시간이면30km 이상’ 같은 거리 하한을 강제하지 않습니다. 도심 신호/혼잡에서는 평균속도와 거리가 낮을 수 있고 원활한 간선·고속에서는 더 길어집니다. 최고속도와 평균속도를 구분합니다. 그래프를 빠르게 보이도록 값만 올리거나 속도와 거리를 따로 조정하지 않습니다.
- 주행 상태표는 RPM 대신 **운행 누적거리(km)**를 표시합니다. 출발 이후 누적이며 선택 조회 구간에서0으로 초기화하지 않습니다. 원본 Microtrip cdit와 Trip dis는 기존 계약대로m입니다. 그래프 시간 눈금은 시작/25%/50%/75%/종료의5개입니다. Trip 상세표를 닫아도 **상세표 다시 열기** 또는 해당 행 선택으로 다시 확인합니다.

검증은 운행 길이 분포·최소 주차·날짜/seed 재현과 시간-속도 적분 거리·정상 가감속·원활 구간 회복을 개발 시험에서 확인합니다. 개인 운전 경험은 가능한 사례의 폭을 확인하는 참고이며 표본 대표성이나 발생확률의 근거로 사용하지 않습니다. 지도/실제 목적지 귀환/실차 보정 완료를 의미하지 않습니다. 사용자용 운행 분포 분석 화면은 추가하지 않습니다.


## 최소·최대 시간으로 운행 배정

새 일정 기본은 **최소·최대 시간 배정(fleet-plan-4)**입니다. `configs/fleet-bounded.example.json`이 현재 예시입니다. 기존 fleet-plan-1/2/3 기록은 원본 설정과 규칙을 보존합니다. 이전 일정을 바꾸려면 **설정 복사 → 운행 시간 배정: 최소·최대 시간 배정 → 최소/최대 지정 → 일정 생성·기록** 순서로 진행합니다.

- 최소·최대는 **운행 1회 전체 시간**입니다. 하루 합계나 측정 기간이 아닙니다. 예를 들어5~40분이면 각 운행 길이가 그 안에서 달라집니다. 기본3~90분은 개발 예시이며, 입력 범위는2~240분/회입니다. 최소=최대도 지원하며 최소>최대는 거절합니다.
- 새 배정은 daily_driving_minutes를 사용하지 않으며 이 값과 함께 요청하면 거절합니다. API에는 fleet_version=fleet-plan-4와 trip_min_minutes/trip_max_minutes를 보냅니다. 구버전/버전 생략 API는 기존 하루 목표 방식을 유지합니다.
- 짧은 용무·일반 이동·긴 이동은 범위 내 서로 다른 길이 구간을 선택합니다. 출퇴근은 차량별 편도 기준을 유지하며 날짜별로 변동합니다. 날짜 편차 뒤에도 최소·최대를 지키고 하루 합계를 정규화하지 않습니다. 주간/비정기형은 자정 내 배치를 위해 가능한 운행 횟수와 길이를 제한하고 최소30분 주차를 확보합니다. 미운행/주말 참여는 별도로 유지합니다.
- 최소시간은 출발부터 종료까지에 적용합니다. 측정 기간이 운행 중간을 잘라 관측한 부분은 최소보다 짧을 수 있습니다. 전체 운행과 관측 시간 모두 화면에서 구분합니다.
- **총주행시간**은 차량·운행 탐색의 출발/종료 옆과 Trip 요약 제목에 표시합니다. 일반 요약은 전체 운행, 시험용 종료 Trip 요약은 stt~edt의 시험 집계 시간입니다. 화면의 보조 표시이며 OBD 원본 JSON·전송 필드를 추가/변경하지 않습니다. 정차·공회전은 시동이 켜진 운행 시간에 포함합니다.
- 일정 주행 상태표와 이전 실행의 상태표 모두 RPM 대신 운행 누적거리(km)를 표시합니다. 원본 메시지의 RPM과 m단위 거리는 그대로입니다. 화면 HTML은 no-store로 제공하며 이미 열어 둔 화면은 한 번 새로고침해야 새 화면 코드가 적용됩니다.
- 긴 운행의 평균속도가 낮다고 거리를 임의로 늘리지는 않습니다. 정체 도로 설정은 혼잡한 운행을 의도하며 저속 평균이 남을 수 있습니다. 새 시간 범위는 장시간 운행을 하루 목표 때문에 강제하는 문제를 없애는 변경이고, 실제 도로의 혼잡 분포를 실차로 보정한 변경은 아닙니다.


### 운행 시간 설정 간소화

현재 새 일정에서 **차량 간 운행 시간 편차**는 제거했습니다. 차량별 출퇴근 기준 길이와 목적별 길이 추첨이 차량 간 차이를 만들며, 별도 duration_preference 계수는 만들지 않습니다. fleet-plan-4 요청에 vehicle_variation_percent를 보내면 안내와 함께 거절합니다. 현재 예시 JSON에도 이 항목은 없습니다. 이전 기록은 재현을 위해 기존 버전과 값을 보존하며 고급 설정에서 당시 값을 확인할 수 있습니다. 새 방식으로 바꾸려면 설정 복사 후 기본 최소·최대 시간 배정을 선택하세요.

**같은 차량의 날짜별 편차(±%)**는 ‘고급 전체 조건’에 있습니다. 기본25%를 유지하며 차량마다 날짜별로0.75~1.25 계수를 정해 그날 운행 길이에 적용합니다. 이 범위와 기본값은 실측 통계가 아닌 개발 설정입니다. 최종 길이는 최소·최대 안에 제한합니다. 0%는 이 날짜 계수만1로 고정하며, 목적별 길이 추첨·출퇴근의 운행별 ±10% 변화·미운행/주말 참여·출발 시각 변화까지 없애지는 않습니다. 매일 동일 운행을 보장하는 옵션이 아닙니다.


### 조회 요약과 도로 성격 해석

상태표·그래프는 조회 대상이 많아도 최대120점의 요약입니다. 원본 Microtrip은 페이지로 조회하며 Trip의 시간·거리·평균은 내부 전체 구간에서 계산합니다. 요약점 수를 줄여도 원본 생성/전송 주기나 Trip 수치는 바뀌지 않습니다.

고속 중심은 합성 경로의 성격입니다. 현재15분미만 운행은 고속 진입 없이 일반도로로 생성될 수 있으므로 고속도로 통과나 높은 평균속도를 보장하지 않습니다. 이 임계값은 실제 지도에서 추정한 값이 아닙니다. 정체 성격은 낮은 평균속도가 남을 수 있으며 최고속도와 평균속도를 구분해야 합니다.


### 운행 선택으로 바로 상세 조회

차량 데이터의 **운행 막대 또는 조회 운행 목록**에서 운행을 선택하면 해당 운행의 전체 관측 구간 OBD를 자동 생성·조회합니다. 선택 직후 별도 생성 버튼을 누를 필요가 없습니다. 이미 조회한 운행은 ‘선택 운행 다시 조회’로 재조회할 수 있습니다. 기록을 열거나 조회 차량을 바꾸기만 했을 때는 첫 운행을 선택만 하며 자동으로 전체 계산하지 않습니다. 이때 첫 막대를 클릭하거나 기존 생성·조회 버튼을 사용하세요.

처음 조회하는 먼 운행은 과거 운행의 누적 상태를 준비하므로 기다릴 수 있습니다. 계산 중 진행 상태를 표시하고 운행 선택을 잠시 비활성화합니다. 전체 차량 OBD를 미리 생성하거나 MQTT로 전송하지 않습니다. 운행을 바꾸면 시험용 종료 Trip 체크가 해제되고 정상 조회로 시작합니다. 필요한 경우 해당 운행에서 시험 옵션을 선택해 다시 조회하세요.

시간선에는 KST 날짜 경계선과 측정 시작/중간3곳/종료의 날짜·시간 눈금이 표시됩니다. 마우스를 올리면 위치에 해당하는 시각과 운행/주차 상태를 확인할 수 있습니다. 운행 막대는 출발·종료·총주행시간을 안내하며 키보드 Tab으로도 확인하고 Enter로 선택할 수 있습니다. 좁은 화면에서는 시간선만 좌우로 스크롤해 눈금을 읽을 수 있습니다. 짧은 운행은 최소2px 표시로 실제 비율보다 조금 넓을 수 있으며 많은 운행이 겹칠 때는 조회 운행 목록을 사용하세요.


## 일정 실행의 지속 생성 세션

저장된 일정에서 전체 일정 실행을 시작하면 기본적으로 Go 생성 프로세스1개를 시작해 여러 페이지를 처리하고 실행 종료 시 닫습니다. 생성 Worker 설정으로2·4개 병렬 실행도 선택할 수 있습니다. 송신 없는 생성 확인과 실제 MQTT 전송 모두 같은 생성 Worker 풀을 사용하며 기본1개입니다. 화면의 선택 운행 조회는 기존 조회 방식을 유지합니다. 대규모 상한 확대는 아직 적용하지 않았습니다. 계획100대/30일/문맥10,000운행, 송신 없는 실행1시간/10,000메시지 및 일반 MQTT 상한은 그대로입니다.

- 같은 운행은 모션·엔진 계산을 재사용합니다. 페이지의 OBD 본문·시각·순서와 최종 Trip은 기존 조회와 같습니다. 실행 전용 응답에는 화면용 그래프 요약을 보내지 않으며, Trip 요약은 마지막 페이지에 전달해 예정 종료 시각에 처리합니다. 종료 전 Microtrip/종료 시 Trip 정책은 유지합니다.
- 캐시는 Worker마다 최대1,024개 운행, 모션·엔진 slice와 문자열 등 보유량 추정32MiB입니다. 이 값은 프로세스 전체 메모리 상한이 아닙니다. 상한을 넘으면 오래 사용하지 않은 운행을 비우며, 필요할 때 같은 조건으로 재계산합니다. 차량이 많으면 캐시 재사용률과 성능 향상이 작아질 수 있습니다. 메시지 전체를 캐시에 저장하지 않습니다.
- 종료·중단·오류 시 프로세스를 정리합니다. 중단은 먼저 종료를 요청하고1초 안에 끝나지 않으면 강제 종료합니다. 응답 ID가 틀리거나 페이지 진행 위치가 맞지 않으면 실패로 종료하며 확인 없이 자동 재실행하지 않습니다. 기존 일정의 일시정지·재개는 페이지 처리 경계에서 적용합니다.
- 결과 JSON의 generation_session은 process_starts(생성 프로세스 시작 수), page_requests(정상 처리한 생성 요청 수·과거 상태 준비 포함), plan_builds(캐시 미사용으로 계산한 횟수), cache_hits(계산 재사용), cache_evictions(캐시 축출), peak_cache_estimated_bytes(캐시 보유량 추정 최대), peak_heap_alloc_bytes(응답 시점 표본에서의 Go 힙 사용 최대), cleanup_confirmed(프로세스/응답 스레드 종료 확인), close_acknowledged(정상 close 응답 확인), forced_termination(강제 종료 여부)을 기록합니다. 캐시 관련 마지막 값0은 정상 종료 시 캐시를 비웠다는 뜻일 수 있습니다. 힙 표본은 OS 작업 메모리와 다릅니다.

변경 전후 전체 페이지 직접 비교(동일 조건·100건 페이지·각3회·로컬 벽시계 중앙값)는10분300건45.45→16.64ms,60분1800건338.22→42.66ms,180분5400건1253.55→120.16ms였습니다. Windows 최대 작업 메모리 중앙값은180분 조건에서14.23→16.18MiB였습니다. 측정은 시작·JSON 응답 처리·종료를 포함하며 단일 운행의 합성 데이터 비교입니다. AWS 성능이나 수천 대 처리 보장이 아니며180분 생성기 시험이1시간 실행 상한 완화를 뜻하지 않습니다.


## 생성 Worker 분할과 제한된 대기열

**저장 일정 → 연결·전송 → 전송 방식 선택 → 생성 Worker 수1·2·4개 선택 → 전체 일정 실행 시작** 순서입니다. 실제 MQTT는 서버 프로필 준비와 실제 송신 확인이 필요합니다. Worker는 기본1개이며 실행 중에는 바꾸지 않습니다. Worker 수는 차량 계산을 나누는 수이고 MQTT Client 수는 연결 배정 수입니다. 예를 들어 Worker2개·Client5개로도 실행할 수 있습니다. 각 일반 MQTT 상한은 별도로 적용합니다.

- 차량은 vehicle_id의 SHA-256 앞8바이트를 Worker 수로 나눈 값으로 실행 전에 고정 배정합니다. 배정표는 generation_pool.assignments에 기록합니다. Worker 수가 달라도 차량별 seed·시각·운행번호·OBD 본문은 바뀌지 않습니다. Worker 오류 시 전체 실행을 중단하며 자동 재배정하지 않습니다.
- 실행기는 전체 차량의 운행 목록을 복사해 보관하는 대신 차량별 현재 운행을 처리하고 다음 운행을 순차로 꺼냅니다. 자동 일정의 날짜 경계 정렬에는 제한된 날짜 문맥을 사용합니다. 저장된 수동 일정 원본과 공통 생성기의 입력 검증·과거 상태 복원용 임시 계산은 남아 있습니다. 이 변경이 모든 메모리 비용을 제거한 것은 아닙니다.
- 기본 대기열 예산은2000건/8MiB입니다. 준비된 메시지 외에 진행 중 응답·완료 Future와 소비 중 메시지의 바이트 credit도 먼저 예약합니다. 바이트 값은 UTF-8 JSON 데이터와 응답 예약 기준이며, Python 객체 오버헤드·모션 캐시·Go 런타임을 포함한 전체 RAM 상한이 아닙니다.
- 차량 수/Worker 수/예산에 따라 요청당 페이지 상한을1~100건으로 조절합니다. Go도 응답의 바이트 예산에 맞게 페이지를 더 작게 나누며 다음 위치를 확인합니다. 필요한 페이지가 준비되거나 소비될 때까지 생산을 기다리게 하며 원본을 임의 폐기하지 않습니다. 실시간 실행에서는 예정 시각2초 전부터 준비를 요청할 수 있습니다. 한 페이지가 담는 미래 메시지 전체가2초로 제한되는 것은 아닙니다.
- API의 generation_workers는 정수1/2/4, generation_queue_messages는256~2000, generation_queue_bytes는4~16MiB 범위이며 송신 없는 실행과 실제 MQTT에 모두 적용합니다. 화면에는 Worker 수만 노출하며 대기열 기본 예산은 서버가 적용합니다. 계획100대/30일/문맥10,000운행, 송신 없는 실행1시간/10,000메시지, 일반 MQTT 상한은 유지합니다.
- 실행용 중간 상태는 최대256개의 작은 차량 종료 상태로 메모리에 보관하고 실행 뒤 폐기합니다. 화면의 조회 캐시와 분리했으므로 조회 캐시 삭제가 실행 상태를 지우지 않습니다. 전체 메시지를 DB에 추가 저장하지 않습니다.
- 일시정지 중에는 새 페이지를 요청하지 않고, 이미 진행 중인 페이지는 준비를 마칠 수 있습니다. 중단·오류 시 모든 Worker를 정리하고 남은 대기 메시지·예약량을 해제합니다. 중단 때문에 폐기한 미처리 데이터는 집계하며 정상 완료의 데이터 누락과 구분합니다. 정상 종료 Trip을 임의로 추가하지 않습니다.

결과 JSON의 generation_pool에는 고정배정, Worker별 요청·계산 재사용·처리 경과시간(work_ms), 실행 중간 상태 개수와 대기열 집계를 기록합니다. queue.peak_reserved_messages/peak_reserved_bytes는 준비된 데이터·진행 중 응답 예약·소비 중 데이터를 포함한 최대 credit입니다. queued_*는 준비된 메시지, max_*는설정 상한입니다. 중단 시 discarded_queued_*와 cancelled_page_requests로 남은 미처리 분량을 구분합니다. generation_session은 Worker별 집계를 합한 호환 요약이며, peak_active_workers는 동시에 활성화된 생성 요청 수로 CPU 코어 사용률이 아닙니다. Worker별 피크를 더한 값도 정확히 같은 시각의 프로세스 메모리 최대값을 뜻하지 않습니다.

로컬 비교(각3회 중앙값, 시작·생성·시각순 처리·종료 포함)에서8대10분2408건은 Worker1/2/4개로834/564/414ms, 종료 직전 생성 프로세스들의 작업 메모리 합계는약14/27/52MiB였습니다. 32대의24시간 운행 중10분을 관측한9632건은15.4/10.6/7.1초, 약84/167/314MiB였습니다. 후자는 긴 모션 계산의 재사용·축출 비용을 드러내는 조건이며 일반 운행 비율이 아닙니다. 모두 송신 없는 로컬 시험이고 AWS 성능 또는 수천 대 지원 보장이 아닙니다. Worker를 늘리면 메모리와 CPU 비용이 커지므로 기본1개를 유지합니다.

## 생성 Worker 풀과 일정 MQTT 통합

일정 MQTT도 **저장 일정 → 생성 Worker 풀 → 생성 대기열 → 고정 Client별 송신 대기열 → MQTT 브로커/IoT Core** 흐름을 사용합니다. 생성 Worker1·2·4개는 계산용 Go 프로세스 수이며, 별도의 송신 Go 프로세스1개가 고정 배정된 여러 Client를 관리합니다. Worker 수를 바꿔도 차량별 생성값·시각·발행 순서는 유지합니다. 생성 Worker와 Client의 배정은 서로 독립적이며 실행 중 증감·재배정하지 않습니다. 이전 실행 기록은 자동 변환하지 않습니다.

- MQTT 실행도 차량별 현재/다음 운행을 순차로 읽고 실행 전용 중간 상태를 사용합니다. 조회용 캐시 삭제가 실행 필수 상태를 지우지 않습니다. 화면 조회와 같은 OBD 생성 규칙을 사용하고 내부 도로·상황 정보는 payload에 넣지 않습니다. Microtrip은 종료 전, 정상 Trip은 운행 종료 시에만 처리합니다. 측정 끝의 미종료 운행이나 실행 중단에 가짜 Trip을 추가하지 않습니다.
- 운행 시작·메시지·운행 종료를 시각순으로 합쳐 처리합니다. 같은 시각에는 시작→메시지→종료 순서이고, 같은 Client에 배정된 차량의 관측 운행 구간 합집합을 유지합니다. 생성이 늦거나 PUBACK이 지연돼도 해당 Client의 기존 대기 메시지 뒤에 연결 해제를 넣습니다. 전체 경계 목록을 실행기에 복사하지 않고 차량별 경계를 순차로 꺼냅니다.
- 송신 대기열이 가득 차면 생성 결과의 추가 인출이 멈춥니다. 이미 진행 중인 생성 응답은 미리 예약한 범위 안에서 완료할 수 있으며 새 생성 요청은 계속 쌓이지 않습니다. 생성 기본2000건/8MiB와 송신100명령/1MiB를 각각 제한하므로 통합 예약 상한은2100건/9MiB입니다. API에서 생성 예산을 변경하면 통합 상한도 그 합계로 바뀝니다. 남는 송신 예산을 생성에 빌려주는 동적 공유 방식은 아닙니다.
- 통합 예약은 생성된 메시지뿐 아니라 생성 응답의 원문·디코딩 예약, 인출 중 메시지, 송신 대기·진행·연결 명령의 직렬화 크기 credit을 합산합니다. 구간 사이에 인계 중인 데이터는 보수적으로 양쪽에 잡힐 수 있습니다. 전체 Python/Go RAM, 모션 캐시, 객체 오버헤드, MQTT 라이브러리의 통신 버퍼를9MiB로 제한하는 의미는 아닙니다.
- 일시정지는 새 생성 요청·송신 명령 시작을 멈추고 진행 송신 응답을 집계한 뒤 완료합니다. 이미 시작한 생성 작업은 예약 안에서 완료하거나 다음 작업 경계에서 기다립니다. 대기는 보존하고 재개 시 이어 처리합니다. 중단·생성 오류·전송 오류에는 전체 실행을 정리하며 자동 재배정·재실행·미확인 재발행을 하지 않습니다.
- 결과 buffer_budget의 reserved_messages/reserved_bytes는 현재 두 구간의 합계, peak_reserved_*는 같은 시각의 합계 최대값, max_messages/max_bytes는 두 예산의 합계 상한입니다. generation_reserved_*와 transmission_reserved_*로 각 구간을 구분합니다. 실행 결과의 상세 처리 결과와 연결 상태에서 통합 예약을 확인할 수 있습니다. execution_cleanup_confirmed는 생성 작업·프로세스와 송신 프로세스·연결을 정리했는지 표시하고, 정상 완료에는 별도로 각 세션의 종료 응답도 필요합니다. 오류·중단 후 예약량은0으로 정리합니다.
- 상태는 메시지마다 DB에 저장하지 않습니다. MQTT 명령 진행 중에는 최대10회/초, 그 외에는 기본0.5초 간격으로 진행 상태를 저장하며 경계·일시정지·최종 상태 등은 즉시 기록할 수 있습니다. DB에는 기존 원본 일정·고정 배정·집계·제한 샘플만 남기고 전체 전송 원문을 추가 저장하지 않습니다.

일반 MQTT 최대20 Client/100메시지/30초와 서버의 더 작은 설정 상한을 유지합니다. 통합은 장기 실행·수천 대 지원이나 실제 AWS 접속 검증을 뜻하지 않습니다. 실제 AWS 시험은 endpoint·정책·인증서·수신 규격이 준비된 뒤 수행합니다.

## 일정 생성·MQTT 통합 경로의 성능 측정

Windows에서는 `.venv/Scripts/python.exe scripts/measure_schedule.py`를 실행합니다. 설정을 바꾸려면 `--config configs/schedule-measurement.example.json`처럼 JSON 파일을 지정하세요. Linux에서는 프로젝트 가상환경의 Python을 사용합니다. 자원 계측 코드는 Windows/Linux 경로가 있으며 이번 실행 검증은 Windows11에서 수행했습니다. 별도 UI나 실행 중인 제어 서버는 필요 없고 프로젝트의 Go/Python 의존성이 필요합니다.

기존 measure_mqtt.py의 단일 운행 시험과 달리 저장 일정 API → 생성 Worker 풀 → 시각순 대기열 → Client별 MQTT 송신 경로를 직접 실행합니다. 조건마다 격리된 제어기·생성/송신 프로세스, 일회성 루프백 mTLS 브로커, 임시 실행 DB를 만들고 종료합니다. 사용자 서버의 DB/접속 프로필과 AWS를 사용하지 않습니다. 입력에 broker_url·인증서·외부 주소를 지정할 수 없으며 내부 프로필도 루프백 IP와 일반 MQTT 상한으로 재검사합니다. 다른 파일을 수정하는 내부 실행 인자 사용은 허용하지 않습니다.

예시는18조건을2회씩 순차 실행합니다. 동일 seed42·mixed 도로·차량 동시 출발, 측정6초/관측 운행4초/주기1초를 고정해 차량당 Microtrip4건+정상Trip1건을 비교합니다. 기본10대의 Worker1/2/4×Client2/10×기간 내내/운행 중 유지12조건, 관측 전120분의 운행 문맥3조건,20대의 Client4/20 두 조건과 ACK20ms 지연1조건입니다.120분 문맥은120분 동안 연결해 실행하는 시험이 아닙니다. 큰 규모를 허용하기 위한 설정이나 실제 교통 분포의 대표성 시험도 아닙니다.

|JSON 항목|범위와 의미|
|---|---|
|repeats|1~3, 기본2|
|cases|서로 다른 이름의 조건1~24개|
|name|1~60자. 표의 구분 기호/줄바꿈 제외|
|vehicles / clients|각1~20, Client≤차량. 같으면 차량별 전체 연결, 작으면 고정 연결 풀|

|lifetime|always 또는 while_driving, 기본always|

|fault|none 또는 delay_ack(20ms), 기본none|

프로필은 최대20 Client/100건/30초·초당5접속/70발행으로 제한합니다. 기존 확장 로컬 측정 프로필의 더 큰 한도를 사용하지 않습니다. 정상 입력은 한 회차에 차량당5건, 전체 최대100건입니다. 조건은 짧은 소량 비교에 맞춰 제한했으며 이 도구로 일반 송신 상한을 해제하지 않습니다.

결과는 `.local/measurements/schedule-<KST시각>-<식별자>/`에 저장됩니다. summary.json은 회차별 집계, summary.md는 읽기용 표, comparison.json은 조건별 중앙값·최소/최대와 동일 생성 조건의 지문 일치 여부입니다. 중간 결과도 회차 완료마다 저장합니다. 전체 메시지·인증서·개인 키·접속 프로필·임시 실행 DB는 결과로 보관하지 않습니다. 원문 대신 정규화한 메시지의 집계 지문과 건수, 토픽별 시각 역전/종료 후 발행 횟수를 확인합니다. 입력·수신 지문은 집합 기준이고 서로 다른 Client 간 도착 순서를 강제하지 않습니다. 잘못된 입력/전송·정리·측정 누락/지문 불일치에는 실패 종료 코드를 반환합니다. 운영 상한 승인은 자동으로 내리지 않습니다.

CPU는 제어기·생성 Worker·송신 프로세스별 누적 시간과 합계를 기록하며100%는 코어1개 기준입니다. 제어기에는 계측 및 가상 HTTP TestClient의50ms 조회 부하도 포함합니다. 이를 그대로 실제 배포 서버 CPU 비용으로 환산하지 마세요. 브로커는 합계에서 제외합니다. 메모리는100ms마다 살아 있는 프로세스들의 현재 RSS를 더한 후 최댓값을 구합니다. 공유 페이지 중복이 가능하며 고유 RAM/컨테이너 청구량·서로 다른 시점의 개별 최대값 합계와 다릅니다. 짧은 작업의 CPU0이나 샘플 사이 피크 누락 가능성도 해석에 반영해야 합니다. 지표 정의는 [GetProcessTimes](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getprocesstimes)와 [Working Set](https://learn.microsoft.com/en-us/windows/win32/memory/working-set)을 참고했습니다.

측정값에는 최초 접속과 데이터 준비 시간이 포함됩니다. 초당5개 접속 제한 아래에서 Client20개를 동시에 시작하면 마지막 접속 시작까지 약3.8초가 필요하므로 초기 지연과 정상 재생 지연을 구분해야 합니다. 실시간6초·소수 반복의 결과는 최대 처리량, 장기 안정성, 한국 실차 대표성 또는 AWS 성능을 보장하지 않습니다. 규모를 늘릴 때는 정확성·예약 상한·중단/정리·지연·CPU/메모리 여유와 연속 실행을 별도로 확인해야 합니다.

## 로컬 전용 1,000대 확장 시험

`.venv/Scripts/python.exe scripts/measure_schedule.py --config configs/schedule-scale.example.json`으로 실행합니다. 각 조건에 `local_scale: true`를 명시한 경우만 vehicles/clients 각각1~1000을 허용합니다. 플래그가 없으면 기존1~20 범위를 유지합니다. 공개 HTTP API의 계획100대·일반 MQTT20 Client/100건/30초 상한은 변경하지 않습니다.

확장 입구는 시험 도구 내부에서 차량별 기존 ScheduleRequest/주차 계약을 검증하고 공통 JobManager·생성 풀·송신 엔진으로 전달합니다. 공개 계획 API가1000대를 허용하는 방식은 아닙니다. 입력 전체의 차량ID 중복/문맥 운행10000회/예정 메시지10000건도 검사합니다. 임의 broker_url 입력은 거절하고 직접 생성한 루프백 IP의 mTLS 프로필만 사용합니다. Go 코어도 local_benchmark가 켜진 루프백 연결에만1000 Client/10000건/120초/200접속·5000발행 한도를 허용하며 외부 주소는 거절합니다. 실제 AWS로 이 확장 한도를 사용할 수 없습니다.

확장 예시는100→250→500→1000대에서 풀10개와 차량별 전체 연결을 비교하고1000대·풀10개에서 Worker1/2/4를 비교합니다. 현재 예시는 각1회입니다. 관측 구간14초, 실제 운행12초, 주기2초로 차량당 Microtrip6건+종료Trip1건이며1000대면7000건입니다. 접속과 처리가 늦어지면 실제 실행은14초보다 길어지며120초 제한을 적용합니다. 전송 완료와 실시간 주기 준수는 별도 판정해야 합니다. 일반6초·초당5접속 측정과 접속 속도/주기가 다르므로 단순 성능 우열로 비교하지 않습니다.

생성 페이지는 차량 수가 많으면1건까지 작게 나눕니다. 각 차량의 최대 페이지 공간을 모두 한꺼번에 예약하지 않고 실제 준비/계산 응답을 건수·바이트로 제한합니다. 가장 이른 미준비 차량의 응답 공간을 남겨, 뒤 시각 데이터가 예산을 차지해 순서 처리가 막히는 것을 방지합니다. 기본 생성2000건/8MiB·송신100명령/1MiB 제한은 유지합니다. 전체 RAM 상한을 의미하지 않습니다.

지속 생성 세션은 실행 파일 해시를 시작할 때 한 번 구하고, 경로·파일 식별/크기/시간 정보를 확인해 변경을 감지합니다. 파일이 달라지면 실패로 정리하며 확인 없이 다른 엔진으로 이어가지 않습니다. 일반 단발 조회의 전체 해시 검사와 데이터 생성 규칙은 유지합니다. 이 최적화는 실행 중인 신뢰된 빌드 파일의 식별을 위한 것이며 페이지마다 실행 파일 전체를 다시 읽는 비용을 줄입니다.

결과의 initial_connect_ms는 송신 세션 시작부터 모든 고정 Client의 최초 접속을 확인하기까지의 시간입니다. post_connect_schedule은 일시정지를 보정한 예정 시각이 전체 최초 접속 완료 이후인 메시지들의 발행 지연 요약입니다. 이미 밀린 이전 시각의 메시지는 이 구분에서 제외합니다. count0이면 비교할 표본이 없다는 뜻이며 지연0으로 해석하지 않습니다. 이 값이 정상상태의 지속 성능을 보장하는 것은 아닙니다. 비교 파일에는 초기 접속과 이후 지연의 P95 상한을 별도로 기록합니다.

### 대규모 실행 지연 조사

일정 계측 명령에 `--profile`을 추가하면 제어 실행 스레드의 호출 스택을20ms 간격으로 표본 수집합니다. 결과의 `control_profile`은 대기·통신·상태 저장을 포함한 벽시계 표본이며 함수별 CPU 시간이나 정확한 실행 횟수가 아닙니다. 표본 수집 자체의 부하가 있으므로 성능 비교 양쪽에 같은 옵션을 사용하세요. 원본 메시지나 인증서 내용은 수집하지 않습니다. 프로파일 실행이 시간 제한을 넘으면 로컬 `.local/schedule-profile-timeout.log`에 진단 스택을 보관할 수 있습니다.

생성 대기열은 차량별 다음 시각을 색인으로 관리하고 변경된 차량만 갱신합니다. Worker별로 가장 이른 준비 요청을 선택하며, 먼저 보내야 할 차량의 응답 공간을 남깁니다. 생성 완료는 고정 대기시간이 끝나기를 기다리지 않고 완료 알림으로 이어받습니다. 시각·차량 순서, 생성/송신 예약 예산, 고정 Worker/Client 배정, 종료 시 정리 원칙은 그대로입니다.

접속·해제가 몰릴 때 실행 상태는100ms 간격으로 묶어 저장합니다. 최종 완료·중단·오류 결과는 즉시 저장하며, MQTT 발행·응답 집계와 중단 확인을 건너뛰지 않습니다.

### 생성 구간별 시간 해석

일정 실행 결과의 `generation_session`에 생성 요청·계산·응답의 누적 시간을 기록합니다. `generation_task_ms`는 생성 Worker별 작업 호출의 벽시계 시간 합계입니다. `page_roundtrip_ms`는 페이지 요청 시작부터 응답 검사가 끝날 때까지이며, `request_write_ms`는 요청 JSON 변환과 파이프 쓰기, `response_wait_ms`는 응답 대기, `response_decode_ms`는 응답 reader의 JSON 해석 시간입니다. 응답 해석은 초기·종료 응답도 포함합니다. `worker_identity_ms`는 실행 파일 경로·파일 식별 확인 시간입니다. `request_preparation_ms`는 작업 시간에서 페이지 왕복을 뺀 나머지로, Python의 요청 준비·일정 검사·상태 복원·응답 후처리와 일시정지 대기도 포함합니다.

Go가 기록하는 `worker_compute_ms`는 공통 생성 함수, `worker_serialize_ms`는 바이트 페이지 분할을 위한 메시지 변환과 응답 JSON 변환, `worker_stats_ms`는 메모리 표본 수집에 걸린 시간입니다. 모두 경과 시간이며 CPU 시간이 아닙니다. Worker들이 병행하므로 누적 합계가 전체 실행 시간보다 클 수 있습니다. 응답 대기에는 Go 계산과 변환·전달·Python 해석이 겹쳐 포함되므로 이 지표들을 단순 합산하지 마세요.

`execution_timing`은 실행 준비(`preparation_ms`), 생성·송신 명령 처리(`replay_ms`), 남은 측정 기간 대기(`measurement_wait_ms`), 송신 응답 마무리(`drain_ms`), 프로세스·연결 정리(`cleanup_ms`)로 나눕니다. 준비에는 Worker 시작과 최초 연결 명령 등록이 들어가지만 모든 Client 접속 완료를 뜻하지는 않습니다. 전체 최초 접속은 기존 `initial_connect_ms`로 확인합니다. 실패·중단 때 완료하지 못한 구간의 시간은 없을 수 있습니다.

기본 확장 계측의 14초는 12초 운행과 이후 2초를 포함한 관측 기간입니다. 실시간 전송을 평가할 때는 메시지별 예정 시각 대비 발행 지연과 실행 준비·마무리 시간을 함께 확인하세요.

수동 일정 실행은 Worker마다 검증한 운행 문맥을 최대 1,024개 보관하며, 운행 목록이 16건을 넘는 항목은 저장하지 않습니다. OBD 메시지와 복원 상태는 이 캐시에 들어가지 않습니다. `generation_session`의 `prepared_trip_hits`와 `prepared_trip_misses`는 일정 문맥 재사용 횟수와 준비 횟수입니다. `schedule_context_ms`, `checkpoint_restore_ms`, `request_payload_ms`, `checkpoint_update_ms`는 각각 일정 문맥 확인, 중간 상태 조회 및 복원, 요청 구성, 중간 상태 갱신의 Worker별 누적 경과 시간입니다.

지속 전송 예시는 `.venv/Scripts/python.exe scripts/measure_schedule.py --config configs/schedule-sustained.example.json`으로 실행합니다. 로컬 확장 설정에서 `driving_seconds`를 12~90초로 정하며 차량 전체 메시지는 10,000건 이하입니다. 예시는 160대가 90초 동안 2초마다 Microtrip을 보내고 종료 Trip을 한 건씩 보내는 설정입니다. 연결 방식별로 7,360건을 확인합니다.

`publish_windows`는 송신 Worker 시작을 기준으로 10초마다 발행 건수·평균·최대·P95 상한을 집계합니다. `rss_windows`는 자원 수집 시작을 기준으로 10초마다 제어기와 Worker의 동시 RSS 합계 최솟값·최댓값을 기록합니다. 두 지표의 시간 원점은 다릅니다. 마지막 메모리 구간은 종료 정리도 포함할 수 있습니다.

분산 출발은 `.venv/Scripts/python.exe scripts/measure_schedule.py --config configs/schedule-staggered.example.json`으로 확인합니다. `departure_groups`를 지정하면 로컬 확장 시험에서 차량을 2~5개 그룹으로 나눠 20초 간격으로 출발시킵니다. 각 차량은 12~15초 동안 한 번 운행합니다. 예시는 40대씩 네 그룹과 운행 중 연결 설정으로 구성됩니다.

`idle_gaps`에는 그룹 사이의 진행 상태 표본 수와 대기열 예약이 0이었던 표본 수를 기록합니다. 운행 중에만 연결하는 예시에서는 활성 Client가 0이었던 표본도 확인합니다. 연결 풀은 다음 그룹을 위해 같은 Client ID를 다시 연결할 수 있습니다. 같은 차량이 30분 주차 후 재출발하는 경계와 운행 상태 연속성은 `test_parked_vehicles_replay_four_trips_with_continuous_state`에서 가상 시간으로 검증합니다.

같은 차량으로 실제 주차 대기를 검증하려면 `.venv/Scripts/python.exe scripts/measure_schedule.py --config configs/schedule-parking.example.json`을 실행합니다. 예시는 차량 4대가 12초 운행을 두 번 하며, 첫 운행 종료와 재출발 사이에 30분 2초를 둡니다. 연결 해제 처리 시간을 빼고도 실제로 30분 이상 연결이 닫혀 있었는지를 확인합니다. 연결 풀과 차량별 연결은 서로 다른 로컬 브로커에서 동시에 실행되며 약 31분 걸립니다.

이 시험에는 별도로 빌드되는 루프백 전용 Worker가 사용됩니다. 장시간 프로필은 최대 8개 Client, 128건, 1,880초입니다. 일반 실행과 기존 로컬 계측의 제한은 각 실행 방식에 따릅니다. 결과에는 Client별 두 접속의 처리 시간과 실제 미접속 시간, 차량별 첫 Microtrip 두 건의 발행 지연, 주차 중 연결·대기열 상태, 1초마다 표본을 모은 10초 구간별 RSS가 들어갑니다. 접속 처리 시간은 송신 Worker가 명령을 시작한 시점부터 접속 확인까지로 접속 속도 제한 대기를 포함합니다. 프로세스 시작을 기준으로 한 전체 최초 접속 시간과는 별도로 기록됩니다.
압축 반복 시험은 `.venv/Scripts/python.exe scripts/measure_schedule.py --config configs/schedule-compressed.example.json`으로 실행합니다. 1,000대가 4초씩 3회 운행하며, 차량당 회차별 Microtrip 2건과 종료 Trip 1건을 전송합니다. OBD 본문과 상태 복원에는 30분 2초 주차를 포함한 원래 일정을 사용합니다. 로컬 MQTT 발행 예정은 0·35·70초이며, 접속이 지연되면 그 시간도 발행 지연에 반영됩니다. 두 연결 방식은 순차 실행합니다.

압축 시험의 기준은 구성별 9,000건, 같은 차량의 위치·누적거리 연속성, 동일 Client ID의 회차별 접속, 회차 사이 활성 연결·예약 0, 종료 정리입니다. `publish_windows`의 지연은 실제 발행한 10초 구간의 집계이며, 밀린 발행은 다음 구간에 기록될 수 있습니다. 실제 30분 유휴 시간 그 자체는 장시간 주차 시험으로 확인합니다.

발행 지연은 실행 시작에 고정한 원점과 메시지 예정 오프셋을 기준으로 계산합니다. 일시정지 누적 시간은 원점에 더합니다. 송신 처리와 응답 회수 중 걸린 시간은 지연에 포함됩니다. 계측 결과의 environment.schedule_deadline_basis에서 계산 기준을 확인할 수 있습니다.
