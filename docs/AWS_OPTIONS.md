# MQTT 연결 모델과 AWS 실행 환경 비교

작성일: 2026-11-16. 후속 사용자 확정: 코드 스택과 연결 풀 채택. AWS 최종 환경은 추후 선택한다. 아래 비교는 결정 근거 기록이다.

## 판단

Fargate/EC2 중 최종 운영 환경은 지금 확정할 필요가 없다. 장시간 실행 가능한 Linux 컨테이너, 외부 상태 저장, 명시적 자원 제한, 종료·복구 계약은 초기 구현부터 반영해야 한다. 첫 AWS 연결 시험 전에는 임시 실행 환경·리전·네트워크·인증을 정하고, 대규모 분산 실행과 배포 자동화 완성 전에는 실제 측정으로 운영 환경을 확정한다. 배포 마지막 날까지 모든 선택을 미루는 방식은 부적절하다.

## 연결 풀

연결은 MQTT Client와 IoT Core 사이에 유지하는 TLS 통신 경로다. 풀은 여러 차량이 사용할 경로를 미리 여러 개 열고 유지하는 방식이다. 별도 AWS 서비스가 아니라 Go Worker 내부 기능이다. 연결 하나마다 여러 Publish를 순차·비동기로 보낼 수 있으며, 여러 차량 데이터를 합쳐 한 메시지로 만드는 배치와는 다른 개념이다.

예시: 차량 10,000대가 10초마다 1건이면 평균 1,000 Publish/s다. 차량별 연결은 10,000연결이고, 풀에서 연결당 50/s로 배분하면 산술상 20연결이다. 실제 연결 수는 payload 크기·응답지연·미확인 요청·재시도 여유와 다른 할당량을 반영해 측정한다. 차량별 토픽과 상태는 유지한다.

| 모델 | 장점 | 한계 |
|---|---|---|
| 연결 풀 | 연결·TLS 관리 부담 감소, 차량 수와 전송량을 별도 제어 | 차량별 접속·인증·재연결 상황 재현 불가, 한 연결 장애가 여러 차량에 영향 |
| 차량별 연결 | 고유 Client ID, 차량별 연결·인증 모사 | 연결·인증서·메모리 관리 비용 및 접속 폭주 제어 필요 |

연결 풀은 여러 차량 토픽을 발행하도록 허용된 시뮬레이터 인증 정책이 있어야 한다. 정책이 단말 하나와 토픽 하나만 허용한다면 그대로 사용할 수 없다. 연결별 Client ID는 고유하게 하고 차량→연결 매핑을 안정적으로 유지한다. 같은 연결 사용만으로 재시도·장애 시 엄격한 순서나 중복 없음이 보장되지는 않는다.

AWS IoT Core 공식 할당량 기준 연결당 Publish 상한은 100/s이며 계정별 제한도 별도다. 연결을 늘려도 계정 한도가 자동 증가하지 않는다. 근거: [IoT 할당량](https://docs.aws.amazon.com/general/latest/gr/iot-core.html).

## 서비스의 역할

- EC2: CPU·메모리·네트워크를 갖춘 가상 서버. 운영자가 OS와 실행 환경을 관리한다.
- 컨테이너: Worker와 실행에 필요한 파일을 묶은 배포 단위. Docker 이미지가 설계의 공통 실행 단위다.
- ECS: 컨테이너를 배치·시작·교체하는 관리자. 실행 자원으로 Fargate, EC2 또는 Managed Instances를 사용할 수 있다.
- Fargate: 서버를 직접 관리하지 않고 요청한 CPU·메모리 규모로 컨테이너를 실행하는 자원 제공 방식. 작업이 실행되는 동안 할당 자원에 과금하며, CPU가 놀고 있어도 실행 중이면 비용이 발생한다.
- IoT Core: Worker가 보낸 MQTT 메시지를 수신하는 목적지. Fargate를 골라도 IoT Core가 대체되거나 그 비용이 사라지지 않는다.

근거: [ECS 구성](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/ecs-configuration.html), [Fargate 가격](https://aws.amazon.com/fargate/pricing/).

## 구체적인 후보

| 후보 | 구성 | 장점 | 단점 | 프로젝트 적합성 판단 |
|---|---|---|---|---|
| A. EC2 한 대 + Docker | 서버 1대에 API와 Worker 컨테이너, 상태는 외부 저장 | 구조가 직접적이고 서버 접근·문제 분석 쉬움, 자원 활용률이 높으면 비용 경쟁력 | OS 패치·재시작·배포 직접 관리, 서버 장애 영향 집중, 여러 서버 확장은 추가 작업 | 작고 고정된 규모의 초기 시험 후보 |
| B. ECS + Fargate On-Demand | 관리 API와 Worker 분리, ECS가 Worker 실행·교체 | 서버 관리 부담 감소, 실행별 Worker 증감 용이 | 요청 자원 단위 과금, 지속 고부하에서 더 비쌀 가능성, 호스트 세부 조정 제약 | 초기 AWS 통합시험 우선 후보이며 운영 환경 확정은 아님 |
| C. ECS + 직접 관리 EC2 | EC2 서버군 위에 ECS가 여러 Worker 배치 | 서버 종류·규모 선택, 여러 Worker로 서버 활용 가능, 지속 부하 비용 최적화 여지 | 서버 용량·패치·축소 시 작업 이동 등 운영 복잡성 | 장시간 고부하 운영의 비교 후보 |
| D. ECS Managed Instances | ECS가 사용하는 EC2의 프로비저닝·패치·확장을 AWS가 관리 | EC2 선택 폭과 관리 부담 감소의 절충 | EC2 요금 외 관리 요금, 빈 자원 비용·서비스 제약 검토 필요 | 선택 리전·자원 지원 및 총비용 확인 후 비교 후보 |

위 장단점은 공식 기능과 비용 구조를 이 프로젝트에 적용한 설계 판단이다. 절대적 성능·최저가 순위가 아니다. 근거: [ECS 구성](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/ecs-configuration.html), [ECS 가격](https://aws.amazon.com/ecs/pricing/), [EC2 가격](https://aws.amazon.com/ec2/pricing/on-demand/).

추가 선택지는 AWS Batch다. 시나리오를 완료형 작업으로 등록하고 큐·재시도를 관리하는 데 적합하다. EC2/Fargate 등 실제 실행 자원 위의 작업 관리 방식이므로 별도 서버 종류와 혼동하지 않는다. 현재의 수동 전송·실행 중 TPS 변경·일시중지는 애플리케이션 제어가 필요하므로 초기 기본안으로 추가할 이점은 작다는 판단이다. 근거: [AWS Batch](https://docs.aws.amazon.com/batch/latest/userguide/what-is-batch.html).

Fargate Spot은 할인된 유휴 자원을 쓰며 회수 시 2분 전 안내 후 중단될 수 있다. 지속 TPS 측정의 기본으로 삼지 않고 중단 허용 시나리오의 후속 옵션으로 검토한다. 근거: [Fargate Spot](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/fargate-capacity-providers.html).

일반 Lambda는 최대 15분 실행 제한이 있어 장시간 MQTT 연결·차량 상태를 유지하는 Worker 기본 환경으로 부적합하다. 제어용 짧은 작업에는 별도 검토 가능하다. 근거: [Lambda timeout](https://docs.aws.amazon.com/lambda/latest/dg/configuration-timeout.html).

## 실제 AWS 구성에서 공통으로 필요한 부분

사용자 브라우저 → 인증된 관리 화면/API → 실행 명령·상태 저장소 → Worker → IoT Core.

이미지는 ECR, 상태·시나리오는 DynamoDB, 큰 체크포인트는 S3, 인증서 개인 키는 Secrets Manager, 운영 로그는 CloudWatch를 후보로 유지한다. 이 S3는 시뮬레이터 복구 자료 용도이며 후속 파이프라인 검증과 다르다. 관리 화면·API는 Worker와 분리해 Worker를 종료해도 실행 결과 조회가 가능하게 설계한다. 상세 호스팅은 배포 설계 시 확정한다.

네트워크 선택도 비용에 영향을 준다. 외부 수신을 차단한 공용 IP Worker의 인터넷 출구, 사설 Worker의 NAT 경유, 지원되는 VPC endpoint 구성을 비교한다. NAT는 시간·처리량 비용, 공용 IPv4는 주소 비용, endpoint는 종류별 비용이 있으므로 리전과 실제 송신 경로를 확인해 선택한다. 모든 전송이 NAT를 경유한다고 가정하지 않는다. 근거: [VPC 가격](https://aws.amazon.com/vpc/pricing/).

총비용은 Worker 자원 + IoT 메시지·연결 + 상태/로그 + 네트워크 + API/화면이다. Fargate와 EC2의 서버 요금만 비교하면 판단을 잘못할 수 있다. 측정된 동일 TPS·메시지 크기·QoS·실행시간에서 비용을 산정한다. 목표/리전 미확정 상태에서 임의 월 비용은 제시하지 않는다.

## 결정 시점과 구현 경계

| 시점 | 결정할 것 | 이유 |
|---|---|---|
| 초기 설계·구현 | 장시간 Linux 컨테이너, 외부 상태 저장, 복구·종료 신호 처리, 자원 제한, 인증/토픽 계약 | 늦게 바꾸면 생성·전송·복구 코드에 큰 영향 |
| 첫 AWS 통합시험 전 | 임시 컴퓨팅 환경, 계정/리전, 네트워크 출구, 인증서/권한, 시험 상한·예산 | 실제 연결과 비용 발생에 필수 |
| 단일 Worker 측정 후, 분산 배포 자동화 완성 전 | 운영 실행 환경, 자원 크기·Worker 수, 실행/교체 방식, 네트워크 세부 구성 | 실측 선택 가능하고 인프라 코드의 불필요한 재작업 제한 |
| 운영 규모 확인 후 | Spot·약정 할인·세부 비용 최적화 | 실행량과 중단 허용성을 알아야 판단 가능 |

생성 엔진과 MQTT 전송 코드는 ECS API에 직접 의존하지 않게 한다. 실행 관리 인터페이스만 start/stop/status로 분리하고 첫 배포 후보의 어댑터만 구현한다. 모든 AWS 후보를 동시에 구현할 필요는 없다. Worker 설정은 외부 입력, 로그는 표준 출력, 체크포인트는 외부 저장소를 사용한다.

이렇게 하면 같은 컨테이너를 다른 실행 자원에서 재사용할 수 있다. 다만 네트워크·권한·자원 정의·배포 절차와 성능 검증은 다시 필요하다. Fargate와 EC2 전환이 기존 서비스 설정의 단순 토글이라고 설명하지 않는다. AWS는 Fargate와 Auto Scaling group capacity provider 간 기존 서비스 변경을 제한하므로 새 서비스 배포·상태 인계가 필요할 수 있다.

추천 순서: 공통 실행 계약으로 개발 → 첫 AWS 시험 때 임시 환경 선택 → 단일 Worker 처리량·메모리·네트워크 측정 → 후보별 총비용 비교 → 운영 배포 환경 확정 → 분산 실행 검증. **후속 사용자 결정으로 코드 스택과 연결 풀은 확정되었고 운영 환경은 추후 선택한다.**
