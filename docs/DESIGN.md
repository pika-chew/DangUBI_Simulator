# 차량 데이터 시뮬레이터 설계 초안 v0.1

작성일: 2026-11-16 (Asia/Seoul). 상태: **코드 스택·연결 풀 확정 / 개발 기반 구성 시작 / 수신 계약·성능 목표는 추후 확인**.

## 1. 설계 목표와 범위

실제 차량의 시간에 따른 상태 변화를 모사하고, 1건 수동 전송부터 분산 장시간 트래픽까지 제어하여 AWS IoT Core로 전송한다. 목표 차량 수와 목표 TPS는 서로 다른 설정이다. 성능 수치는 구현 후 실측하며 수십만 TPS 달성을 미리 보장하지 않는다.

Notion 설계제안서 [N1]의 1~6, 8~9절을 기반으로 구체화했다. 7절 데이터·파이프라인 검증, Lambda·Firehose·S3 결과 추적 및 저장률 보고서는 제외한다. 필수 입력 오류 방지와 생성 엔진 자체의 기능 테스트, MQTT 전송 상태 확인은 제품 기능에 필요한 범위로 포함한다. 데이터 이상 주입은 별도 선택 기능이며 초기 필수 구현에서 제외하는 안이다.

## 2. 핸들링할 데이터

Smart Fleet OBD JSON 메시지를 사용한다. 원시 CAN 프레임·ELM327 장치·OBD PID 질의 프로토콜 자체를 모사하지 않는다. 기본 구조는 `ty`, `ts`, `pld`다. 메시지 필드의 근거는 [S1] 7.2.2절이다.

| 메시지 | 필수 payload 필드 | 선택 payload 필드 |
|---|---|---|
| Trip, 표 기준 ty=3 | tid, stt, edt, dis, tdis, fc, stlat, stlon, edlat, edlon, ctp, coe, fct, hsts, mesp, idt, btv, gnv, wut | usm, est, fwv, dtvt |
| Microtrip, 표 기준 ty=4 | tid, lat, lon, clt | fc, lc, cdit, rpm, sp, em, el, xyz, vv, tpos |

기본 정상 프로필은 위치·속도·RPM·엔진 부하·전압·연료·누적거리·이벤트를 함께 생성한다. Trip은 운행 종료 때 내부 누적값으로 계산한다. 좌표는 WGS84, 거리는 m로 관리한다. 시간은 UTC epoch milliseconds를 프로젝트 제안으로 통일하며, UI 시간만 Asia/Seoul로 표시한다. 미명시 단위는 임의 확정하지 않는다.

### 규격 충돌과 처리 제안

[S1]은 OBD 타입 표에서 3/4를 지정하지만 예제는 1/2다. 좌표·전압 등을 Int로 표시하면서 소수 예제를 사용하며, em은 Hexa String 설명과 Int 표기가 충돌한다. xyz도 Int 표기와 문자열 예제가 다르다. 일부 예제는 필수 clt를 생략한다.

초안은 타입 표의 3/4와 필수 필드 목록을 우선한다. 좌표·전압은 number, xyz는 문자열, em은 내부 비트마스크로 계산하고 전송 표현은 수신 계약으로 확정한다. 단위·배율이 불명확한 fc, coe 및 가속도는 계약 확인 전 호환성을 주장하지 않는다. 표/예제 충돌은 스키마 프로필로 분리하며 매 실행에서 사용할 프로필을 고정한다. 임의로 양쪽 메시지를 동시에 보내지 않는다.

차량 식별자는 기본 제안 토픽 `sim/{run_id}/{vehicle_id}/obd`에 둔다. 기존 수신 토픽이 있으면 해당 규칙을 따른다. 본문은 규격을 유지하고 run_id·sequence·schema_version은 실행 기록에 둔다. 부가 Envelope는 별도 합의가 있을 때만 사용한다. tid는 실행 내 충돌 없이 할당한다.

## 3. 데이터 생성 기능

### 수동 모드

외부 JSON Schema로 입력 항목을 구성한다. 필드 수정, 필수 여부·자료형·범위 표시, 전송 JSON 미리보기, 1건/N건 전송을 제공한다. N건은 동일 본문 반복인지 시간·순번 갱신인지 사용자가 선택하며 기본은 갱신이다. 공통 MQTT 발행기를 사용한다.

### 자동 상태 기반 모드

차량 상태는 시동 OFF → 웜업/공회전 → 출발 → 가속 → 정속 → 감속 → 정차 → 운행 종료로 전이한다. 도심·고속·정체 운행 프로필, 운전자 편차, 상태 체류시간, 조건부 분포, 값의 변화율 제한을 설정으로 관리한다. 기본 대상은 내연기관 승용차이며 EV는 후속 별도 프로필이다.

- 속도와 경과시간으로 이동거리를 적분하고 경로 위 위치를 갱신한다. 초기에는 사전 정의 경로/좌표 목록을 사용한다. 지도 경로 API와 실제 교통량 연동은 필수 범위가 아니다.
- RPM·엔진 부하·스로틀은 상태·속도·가속과 연관되도록 계산한다. 시동 OFF와 공회전을 구분한다.
- 연료는 부하·공회전·경과시간을 반영한 근사 모델로 누적한다. 실제 ECU 측정 정밀도의 디지털 트윈은 목표로 하지 않는다.
- Trip 주행거리·평균/최고속도·공회전시간·연료 등은 Microtrip과 같은 내부 상태에서 계산한다. 급가속·급감속 등은 전이와 임계값에서 발생시킨다.
- seed, 시작 시각, 규칙 버전, 경로, 차량별 난수 상태를 기록한다. 동일 입력으로 데이터 값을 재현하며 네트워크 전송 시각까지 동일함을 보장하지 않는다.

데이터 스키마와 생성 규칙을 분리한다. 범위·단위·분포·현실성 임계값은 설정 가능하게 하며, 실차 자료를 확보하기 전에는 공학적 근사 가정으로 표시한다.

## 4. 트래픽 제어 및 전송

### 모드와 단위

TPS는 **초당 MQTT Publish 요청 수**로 정의한다. 차량 샘플 수, 신규 Publish, 재시도, PUBACK 수는 구분해 표시한다.

| 모드 | 동작 |
|---|---|
| 차량 중심 | 차량 수 N과 차량별 주기 I로 기본 부하 N/I를 계산하고 전송 위상에 편차를 둔다. |
| TPS 중심 | 목표 Publish 속도를 기준으로 활성 차량에 공정 배분한다. 차량 주기도 고정한 경우 충돌을 표시하고 실행을 거부하거나 사용자가 주기 변경을 선택하게 한다. |

Trip과 이벤트도 실제 요청량 및 상한에 포함한다. 묶음 전송 시 샘플 처리량과 Publish TPS가 달라진다. 초기 기본값은 묶음 없음이며, 묶음은 수신 계약 확인 후 옵션으로 추가한다.

Steady, Ramp-up/down, Spike, Wave와 시간대별 스케줄을 제공한다. 예약은 EventBridge Scheduler, 초 단위 부하는 Worker 내부 스케줄러가 담당한다. Scheduler는 60초 정밀도이므로 [S7], 정확한 시작이 필요하면 Worker를 먼저 준비하고 내부 기준 시각에 발행을 시작한다.

각 Worker의 Token Bucket 할당 합이 전체 상한을 넘지 않게 한다. 연결별 limiter도 둔다. 재시도는 전체 상한에 포함하고 별도 카운트한다. 시간 계산은 monotonic clock을 사용하고, 지연 후 밀린 데이터를 무제한 따라잡지 않는다. 큐는 건수·바이트·최대 체류시간을 제한하며 기본 초과 정책은 실행 실패 후 정리다. 버림/감속은 명시적으로 선택한 경우에만 적용한다. 목표 미달을 정상 달성으로 표시하지 않는다.

### MQTT와 인증

사용자 확정에 따라 연결 풀을 기본으로 한다. 차량별 연결 모드는 후속 선택 기능으로 남긴다. 연결 풀은 차량별 인증·접속 패턴 재현과 다르다. 고유 Client ID를 실행·Worker·연결 번호로 구성하고 같은 차량의 전송은 같은 연결에 배정한다.

MQTT 3.1.1 over TLS, X.509 인증, 기본 8883 포트를 우선안으로 둔다 [S3, S4]. 계정의 IoT 데이터 엔드포인트, CA, 활성 인증서, 개인 키와 토픽에 제한된 IoT Policy를 사용한다. ECS IAM 역할만으로 X.509 MQTT 인증을 대체하지 않는다. 개인 키는 Secrets Manager 등 별도 저장소에서 읽고 저장소에 커밋하지 않는다.

QoS 1을 기본 제안으로 하고 QoS 0을 옵션으로 둔다. QoS 1 PUBACK는 브로커 확인이며 후속 처리 완료를 의미하지 않는다. 중복 가능성을 기록한다 [S3]. QoS 0은 발행 호출 성공과 수신 성공을 구분한다. retain은 기본 false다. 지수 백오프·jitter, 연결 시도 상한, 전송 timeout, 미확인 전송 수 제한을 둔다.

[S2] 기준 연결당 Publish 100/s, payload 128KB, 계정 inbound 기본 20,000/s(일부 리전 2,000/s)다. 실행 전 실제 계정 할당량과 다른 워크로드 사용량을 확인한다. 100/s는 목표 운용률이 아닌 상한이며 여유를 둔다. 예컨대 연결당 80/s 제안 시 10,000 TPS는 최소 125연결이며 대역폭·응답지연에 따라 더 필요하다. 이는 산술 예시이며 실측 용량이 아니다.

## 5. 아키텍처와 장시간 실행

관리 UI → 제어 API/시나리오 저장소 → 생성·제어 Worker → AWS IoT Core.

관리 UI는 수동 입력, 자동 생성 규칙, 차량 수/TPS, 예약, 시작·일시중지·재개·중단, 전송 현황을 제공한다. 제어 API는 run_id 발급, 설정 검증, 멱등 시작/종료, Worker 할당을 담당한다. 원본 시나리오는 버전 고정하고 실행 중 변경은 새 revision과 적용 시각으로 기록한다.

상태는 draft/scheduled/starting/running/paused/stopping/completed/failed로 관리한다. 중지 시 새 생성부터 멈추고 제한시간 동안 큐를 정리한 뒤 미전송·미확인 수를 보고한다. 일시중지는 기본 시뮬레이션 시간도 정지하며 재개 시 대량 따라잡기를 하지 않는다.

차량별 고정 shard를 배정하고 lease·heartbeat·fencing token으로 중복 소유를 방지한다. 교체 Worker는 상태·난수·누적값 체크포인트를 복원한다. 체크포인트 이후 재발행 가능성을 인정한다. 초기에는 실행 중 자동 shard 재배치를 제한하고 고정 Worker 수를 사용한다. ECS Service의 교체 기능만으로 차량 소유권이 보장된다고 가정하지 않는다.

로컬 VS Code에서는 코드 편집·소규모 기능 테스트만 수행하고 장시간 부하는 AWS에서 실행한다. 관리 UI/API에는 인증을 적용하고 Worker에는 외부 수신 포트를 열 필요가 없다.

Fargate가 항상 최저가는 아니다. 단일 Worker 측정 후 Fargate와 ECS on EC2의 동일 TPS당 비용을 비교한다. 중단 없는 장기 실행은 On-Demand를 우선하고 중단 허용 시험만 Spot 후보로 둔다. 네트워크는 공용 IP와 NAT/VPC endpoint 대안을 비용·보안 조건으로 비교하고 확정한다.

비용 계산은 실행시간×Worker 자원비 + 연결시간 + 메시지 크기별 Publish 비용 + 로그·상태·체크포인트 + 네트워크·IPv4 + 관리 화면/API 비용을 합산한다. IoT 메시지는 5KB 단위 과금이므로 [S6], 작은 메시지도 무료가 아니다. 리전·목표 TPS·평균 크기·기간이 확정되면 최신 단가로 견적을 낸다. 후속 파이프라인 검증은 제외하지만 기존 Rule이 연결되어 있다면 그 실행 비용은 별도로 확인한다.

최대 실행시간·연결 수·TPS·전송건수 상한을 엔진에서 강제하고 예상 비용 한도를 제공한다. 실제 청구 반영은 지연될 수 있으므로 비용 예상값만으로 즉시 차단을 보장하지 않는다.

| 상태 생성 | seed 재현, 상태 전이, 거리 적분, Trip 집계, 시간 연속성 | 고정 가상시간의 기대 결과와 불변조건 확인 |
| 트래픽 | 차량/ TPS 설정 충돌, 스케줄 경계, limiter, 재시도 포함 상한, 큐 초과 | 가상 clock 테스트 및 제한된 실제 부하 측정 |
| 운영 | 중단·재개, 제어 API 중복 요청, 연결 복구, 체크포인트, 중복 shard 방지 | 강제 종료/재연결 시나리오 확인 |
| 확장 | 여러 Worker 합계 속도와 장기 자원 사용 | AWS에서 단계적 증가·장시간 실행 보고 |

초기 제안 측정 구간은 10 → 100 → 1,000 TPS, 장기 시험 24시간이다. 목표를 확정한 뒤 워밍업 제외 60초 구간 평균 ±5% 등 허용오차와 메모리 증가 기준을 합의한다. 해당 수치는 성능 약속이 아니다. 최대 규모 시험은 계정 할당량과 예산 내에서만 수행한다. S3 저장량 대조 테스트는 포함하지 않는다.

## 8. 검토 후 확정할 항목

1. 1차 목표: 차량 수, 동시 연결 수, 평균/최대 TPS, 실행시간, 허용오차.
2. 수신 계약: OBD 타입 3/4 적용 여부, 단위·자료형, 토픽, 식별자 배치, 이벤트 메시지 추가 범위.
3. 현실성 수준: 내연기관 프로필, 경로 입력 방식, 실차 데이터 기반 보정 여부.
4. React/FastAPI/Go 코드 스택은 사용자 확정. AWS 자원은 공통 실행 계약을 먼저 설계하고 첫 AWS 시험 때 임시 선택, 단일 Worker 측정 후 운영 환경 확정하는 안.
5. AWS 리전·대상 계정·예산과 기존 토픽/인증서 정책.

개발 기반 구성을 시작한다. 미확정 값은 설정으로 분리하며 [구현 계획](IMPLEMENTATION.md)의 단계별 선행 조건을 따른다.
