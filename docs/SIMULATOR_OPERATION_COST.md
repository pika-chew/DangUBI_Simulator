# 차량·Client·Worker의 관계와 비용

2026-11-16 설명 보완. 시뮬레이터 본체는 기능 구현 전이며 아래는 구현 예정 구조다. 코드 스택·풀 채택은 유지하고 AWS 최종 환경은 추후 선택한다.

차량 수는 내부 차량 상태 수, Client 수는 IoT Core로 연결되는 MQTT 세션 수, Worker 수는 생성·전송 프로그램 인스턴스 수다. 서로 같은 수가 아니며 Client마다 서버나 공용 IP가 필요한 것도 아니다.

Worker는 차량별 속도·위치·RPM·누적값·다음 생성 시각을 보관하고, 활성 차량의 생성 주기마다 상태를 갱신해 JSON을 만든다. 제한된 큐와 전체/연결별 속도 제어를 거쳐 MQTT Client가 직접 IoT Core로 보낸다. 차량별 상태 수가 늘면 상태 메모리와 생성 계산량이 증가한다. MQTT 연결이 늘면 TLS·소켓·keepalive·미확인 요청·재연결 관리량이 증가한다. 실제 자원 요구량은 측정해야 한다.

풀에서는 차량→담당 Worker→풀 슬롯을 안정적으로 배정한다. 예시 Client ID는 sim-r01-s01-c001이다. 차량별 연결에서는 예시 sim-r01-v0001처럼 차량과 세션을 일대일로 배정한다. 실제 형식은 고유성과 길이·권한 조건을 충족하도록 구현할 때 고정한다. 메시지마다 Client ID를 새로 만들지 않는다. 재연결에는 같은 세션 식별자를 재사용하고 Worker 교체 시 이전 소유자의 전송을 중지해 충돌을 막는다. 차량 ID는 토픽/본문의 데이터 식별, Client ID는 MQTT 접속 식별이다. 인증서는 별도 접속 자격이다.

풀은 메시지를 자동으로 묶지 않는다. 같은 생성 주기·크기·기간이면 차량별 연결과 메시지 수가 같다. IoT 메시지비는 과금 단위 수, 연결비는 실제 연결·분, Fargate 비용은 할당 자원·실행시간에 따른다. 동일 Worker 할당량·실행시간을 유지하면 설정의 차량/Client 수만 늘었다고 Fargate 요금이 자동 증가하지는 않는다. 자원 증설·Worker 추가가 필요할 때 실행비가 바뀐다. 처리 용량 초과를 비용 없이 감당한다고 해석하지 않는다.

비교 예시: 하루 2시간×3일, 2초 주기, 1KB, 하루 종료 Trip 1건, 연결은 모두 동일하게 72시간 유지. 풀은 피크 연결당 50건/s 가정으로 1,000대에 10연결, 10,000대에 100연결을 배정했다. 운행 중에만 연결하는 예시와 혼합하지 않았다.
